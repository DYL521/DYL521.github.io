01.需求分析

系统设计题第一步不是画图，而是先和面试官把范围谈清楚。"设计抖音"可以无限大，一般收敛到以下核心功能。

1.1 功能需求

  • 上传视频：用户拍摄/选择视频，填写描述、话题后发布；
  • 观看视频：上下滑动的推荐流（For You），以及关注流、个人主页作品列表；
  • 互动：点赞、评论、转发、关注；
  • 计数展示：每个视频显示点赞数、评论数、播放数。

不在本次讨论范围（可以主动说明）：直播、电商、私信、广告系统、内容审核的算法细节。

1.2 非功能需求

  • 高可用：看视频是核心路径，宁可推荐不准也不能刷不出来；
  • 低延迟：首帧时间尽量短，滑动下一条要"秒开"；
  • 读远多于写：观看量远大于上传量，是典型读多写少系统；
  • 最终一致即可：点赞数晚几秒更新可以接受，但不能丢视频。

02.容量估算

以下数字全部是假设，只用于推导量级，面试时要说清楚这是假设并和面试官确认。

假设项 取值
日活用户（DAU） 5 亿
人均每天观看视频数 100 条
每天上传视频数 1000 万条
视频平均时长 / 原始大小 30 秒 / 约 20 MB
转码后多清晰度总大小 约为原始的 1.5 倍，即约 30 MB

推算：

  • 观看 QPS：5 亿 × 100 / 86400 ≈ 58 万/秒，高峰按 2~3 倍算，百万级 QPS；
  • 上传 QPS：1000 万 / 86400 ≈ 116/秒，高峰几百/秒；
  • 每日新增存储：1000 万 × (20 MB 原片 + 30 MB 转码) ≈ 500 TB/天，一年约 180 PB 级别；
  • 出口带宽：假设平均每次观看传输 5 MB（很多视频看不完、会选低码率），58 万 × 5 MB ≈ 2.9 TB/s ≈ 23 Tbps —— 这个量级只有 CDN 能扛，源站不可能直接服务。

结论：视频文件走对象存储 + CDN，元数据走数据库 + 缓存，推荐和计数是读压力最大的服务。

04.上传与转码流程

4.1 上传

  1. 客户端调用上传服务申请上传，服务端生成 video_id 和对象存储的预签名 URL；
  2. 客户端直传对象存储（大文件用分片上传，支持断点续传），视频流量不经过业务服务器；
  3. 上传完成后客户端回调"发布"接口，写入元数据（状态 = UPLOADED），并投递一条转码消息到 MQ。
video: {video_id, author_id, desc, status, origin_key, play_urls{}, cover_url, created_at}
status: UPLOADED -> TRANSCODING -> AUDITING -> PUBLISHED / REJECTED

4.2 转码

  • 转码 worker 消费 MQ，用 FFmpeg 之类的工具转出多种清晰度（如 360p/540p/720p/1080p）和编码（H.264 兼容性好，H.265 更省带宽），同时截取封面；
  • 可以切成 HLS/DASH 分片，便于自适应码率和边下边播；
  • 转码是 CPU/GPU 密集型、可水平扩展的离线任务，MQ 削峰，失败重试，任务要幂等（按 video_id + 规格 判断是否已完成）；
  • 转码后进入审核（机审 + 人审），通过后状态改为 PUBLISHED 并推送到推荐候选池。

面试要点：为什么用异步？—— 转码耗时远超 HTTP 请求可接受的时间，同步做会占满连接；异步 + 状态机让用户先看到"发布中"。

05.存储与 CDN

数据 存储选型 理由
视频文件、封面 对象存储（S3/OSS 类） 海量、便宜、高可靠，天然适配 CDN 回源
视频元数据 MySQL 分库分表 或 分布式 KV 按 video_id 分片，读多写少
用户关系（关注） 分库分表 / 图存储 + 缓存 需要查"我关注的人"和"关注我的人"两个方向
评论 MySQL 分库分表 / MongoDB / HBase 按 video_id 聚合查询
计数 Redis + 持久化 KV 高频读写
行为日志 Kafka → 数仓 给推荐模型训练用

CDN 优化点：

  • 冷热分层：新发布和热门视频在 CDN 边缘命中率高；长尾冷视频回源，对象存储可以按访问频率转低频存储降成本；
  • 预热：推荐系统决定要大规模分发某条视频时，可以提前推送到边缘节点；
  • 客户端预加载：当前视频播放时，预先下载下一两条视频的首个分片，这是"秒开"的关键；
  • 防盗链：播放 URL 带签名和过期时间。

06.Feed 流与推荐

6.1 推荐流（For You）

推荐流不是"拉关注的人的视频"，而是从全量视频池中挑选，典型的多阶段漏斗：

  1. 召回：从多路（协同过滤、向量相似、热门、同城、关注作者等）召回几千条候选；
  2. 粗排：轻量模型过滤到几百条；
  3. 精排：复杂模型预估点击、完播、点赞等目标，加权打分；
  4. 重排：打散同作者/同类型、插入新视频冷启动流量、去重（已看过的过滤，常用布隆过滤器）。

Feed 服务每次返回一页（比如 10 条）视频 ID，再批量查元数据缓存组装成响应。用户的观看、完播、滑走等行为实时回流到日志，用于更新特征和模型。

6.2 关注流：推模式 vs 拉模式

  • 推（写扩散）：作者发布时写入每个粉丝的收件箱，读快，但大 V 有千万粉丝时写放大严重；
  • 拉（读扩散）：读的时候合并关注作者的最新作品，写简单，但关注多时读慢；
  • 推拉结合：普通作者推、大 V 拉；或者只给活跃粉丝推。这是面试高频考点。

6.3 降级

推荐服务超时时返回兜底池（预先计算好的热门视频列表，存在缓存里），保证页面不空白。

07.点赞、评论与计数

7.1 点赞

  • 关系数据：like(user_id, video_id, created_at)，唯一索引保证幂等，按 user_id 分片可以快速查"我点赞过的"，判断"是否已赞"可以用 Redis Set/Bitmap 或缓存；
  • 计数：点赞数 不要 每次 UPDATE video SET like_cnt = like_cnt + 1，热门视频会产生严重的行锁竞争。

7.2 计数方案

点赞请求 -> 写点赞关系 -> 发 MQ 事件
                          -> 计数服务消费，内存中按 video_id 合并一段时间（如 1 秒）
                          -> 批量 INCRBY 到 Redis，并异步落库
  • 展示时读 Redis，Redis 缺失再从持久化存储加载；
  • 计数允许短暂不准，但关系数据（是否点赞过）要准确；
  • 定期用关系表全量对账修正计数。

7.3 评论

  • 按 video_id 分片存储，一级评论按时间或热度分页，楼中楼回复折叠，展开时再加载；
  • 分页用游标（上一页最后一条的 (score, comment_id)），避免深分页 OFFSET；
  • 发评论前过敏感词/风控，异步审核。

08.热点问题

抖音天然存在"一条视频突然爆火"的场景：

热点 对策
热门视频元数据读 多级缓存：本地缓存（几秒 TTL）+ Redis；Redis 热 key 可复制多份 key#1..N 随机读
热门视频计数写 计数服务内存聚合后批量写；或把计数拆成多个分片 key，读时求和
热门视频评论 首页评论结果缓存；写入走 MQ 削峰
视频文件带宽 CDN 预热、多 CDN 厂商调度
缓存击穿 热 key 不过期 + 后台刷新，或单飞（singleflight）回源

09.一致性取舍

  • 视频发布：必须可靠，用"状态机 + MQ 至少一次投递 + 幂等消费"保证不丢；
  • 计数：最终一致，允许秒级延迟和短暂误差，靠对账兜底；
  • 点赞关系：用户自己的点赞状态要"读己之写"——写成功后客户端本地先展示，服务端读主库或带版本号缓存；
  • 关注流：推模式下粉丝收件箱延迟几秒可以接受；
  • 删除/下架：需要尽快生效，除了改数据库还要主动刷新 CDN 和缓存。

整体按 CAP 的思路：核心浏览链路偏向 AP（可用性优先），涉及资金、账号安全的部分才要求强一致。

10.面试追问

  • 怎么做到滑动秒开？ CDN 就近 + 预加载下一条首分片 + 自适应码率 + 首帧优先下发。
  • 如何避免重复推荐？ 用户维度的已看集合（布隆过滤器或分段 Bitmap），在重排阶段过滤。
  • 上传一半断网？ 分片上传 + 断点续传，服务端记录已完成分片。
  • 大 V 发视频怎么通知粉丝？ 推拉结合，大 V 走拉模式。
  • 计数服务挂了？ MQ 中消息还在，恢复后继续消费；Redis 丢数据可从持久化存储和关系表重建。

小结

  • 先界定范围，再用标明假设的估算得出关键结论：视频走对象存储 + CDN、读多写少、百万级 QPS；
  • 上传用预签名直传，转码用 MQ 异步 + 状态机 + 幂等；
  • 推荐流是召回 → 排序 → 重排的漏斗，关注流考察推拉结合；
  • 计数、热点靠异步聚合、多级缓存、key 拆分解决；
  • 一致性按业务分级：发布不丢、计数最终一致、个人状态读己之写。
