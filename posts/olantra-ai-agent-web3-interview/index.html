Olantra AI Agent Web3 后端面试准备：岗位分析与项目化回答

面试题 2026-09-08 · 80 min read · 23720 words

这份准备材料面向 Olantra 的 AI Agent Web3 后端工程师岗位，基于收到的 JD 和仓库内 2026 年 9 月版个人简历整理。包含 80 道问题：60 道岗位与技术题、20 道综合场景题，以及项目化参考回答、常见追问、系统设计题和复习清单。

这里的“常见题”是围绕此类岗位核心能力整理的代表性题型，不是 Olantra 内部题库，也没有经过市场频率统计。涉及框架行为的内容参考官方资料；具体版本仍需结合目标项目确认。

一、JD 分析：面试官想找什么人

岗位涉及 Polymarket、DeFi、NFT、GameFi，以及 Agent 工作流、链上数据接入、RAG、模型接入、状态管理、服务部署和性能优化。重点在于将业务需求独立转化为可靠服务，而不是只会搭建聊天 Demo。

使用回答时的真实性边界

  • 已有经历：来自个人简历，包括 mate-assist、企业 RAG、Jarvis Registry、集度研发效能平台和酒店 SaaS。
  • 拟采用方案：Web3、Polymarket、交易签名等回答使用“我会”，不能改成“我已经在生产实现”。
  • 需要补证据：具体事故过程、吞吐量、成本、P95、准确率及个人贡献边界，需要按真实记录补充。
  • Go 经验：当前简历主要证明 Python 后端能力，不能仅凭 JD 对技术栈的描述声称有大规模 Go 生产经验。
  • 简历中的降延迟、节省预算等结果是个人提供的经历记录，本材料未独立验证。使用时应能解释统计口径；开源 Star 和提交数会变化，不作为固定能力指标。

二、自我介绍与项目深挖

01. 请做一个与岗位相关的自我介绍【P0】

参考回答： 我有 8 年以上 Python 后端和企业平台研发经验，近两年主要做 RAG、Agent 和 MCP 平台工程。目前比较贴合这个岗位的经历有三块：企业 RAG 的多源接入与检索服务；mate-assist 的 LangGraph 对话工作流、状态持久化和 SSE；以及 Jarvis Registry 的 MCP 接入、认证授权和可观测性。

我过去也做过企业系统集成和从 0 到 1 的 SaaS，所以比较关注异步任务、失败恢复、权限和部署这些落地问题。Web3 是我希望进一步深入的业务方向，我会从只读数据分析场景切入，把已有的数据接入和 Agent 工程能力迁移过去，同时补齐链上最终性与交易语义。

追问准备： 选择一个项目继续讲，不要把自我介绍变成框架名称清单。

02. 为什么认为自己适合 Olantra？【P0】

参考回答： JD 需要把数据、模型、工具和后端服务连接起来，这与我最近的工作高度重合。我做过数据源连接器、文档解析、检索重排、MCP 工具授权以及 Agent 状态管理，可以承担从接口到执行链路的设计。

需要承认的差异是业务语义：链上数据存在重组和最终性问题，交易工具也比文档查询更敏感。我会先建立数据正确性和只读分析能力，再与团队确认是否扩展到资产操作。

避免： 因为做过企业连接器，就声称链上索引和钱包系统没有学习成本。

03. 用三分钟介绍 mate-assist【P0】

参考回答： mate-assist 面向汽车销售与经营分析。我的相关工作包括设计 11 节点 LangGraph 对话图，覆盖上下文控制、多模态感知、Query Rewrite、意图路由、RAG 检索与评分、低质量结果重写重检索、生成和长期记忆抽取。

工程上接入了 SSE、首字延迟与整轮耗时指标、节点 Trace、用户中断，以及 MySQL Checkpointer / Store。离线分析由 Celery 执行，配合并发闸门、缓存和 KEDA 扩缩容。这个项目让我形成的经验是：复杂度主要来自状态与失败处理，而不仅是模型能否回答。

追问准备： 画出一个真实分支；解释节点输入输出、失败出口和持久化字段。11 个节点是业务实现结果，不是最佳节点数量。

04. 为什么将 RAG 从 LangChain 迁移到 LlamaIndex？【P0】

参考回答： 我主导过这次迁移，但回答重点应放在数据链路和模块边界。服务被拆分成 API、数据接入、文档解析、Embedding、Retrieval、Reranker 和任务调度，并统一 REST API 与 MCP 查询链路，目的是降低新数据源和模型接入成本。

我不会把优化全部归因于换框架。需要分别说明框架适配、数据处理、查询策略和资源管理的变化，再用同一评测集比较行为、延迟与内存。

必须补充的真实材料： 旧架构具体痛点、迁移切分顺序、接口兼容方案，以及“查询延迟降低约 30%”的样本、分位数和测试环境。简历没有说明采用过双写或灰度，不要将建议方案讲成事实。

05. Jarvis Registry 中你具体做了什么？【P0】

参考回答： 我是核心贡献者，参与 MCP / A2A Gateway 的注册发现、代理接入、身份认证与权限控制等工作。与岗位最相关的是多身份源 OAuth / OIDC、JWT / Session 校验、scope-based RBAC、对象 ACL 和工具级访问控制，以及 Trace、日志和指标建设。

我会挑选一条自己负责的认证或工具调用链路，说明请求如何进入、身份如何建立、权限在哪一层判断、失败如何返回。平台整体能力与个人独立负责的模块要分开说。

追问准备： 准备能公开的 PR 或代码模块。不要用 Star 数代替技术解释。

06. 你能从 0 到 1 独立交付吗？【P0】

参考回答： 我的经历里有酒店 SaaS PMS 与业务中台建设，也有后续框架标准化和 Agent 服务落地。对新项目，我会先明确目标用户、核心任务和验收标准，然后做一条可运行的端到端路径。

第一版把接口、数据模型、认证、异常处理和部署做完整，再依据真实瓶颈拆分服务。不会在业务尚未验证时先建立复杂微服务体系。

追问准备： 酒店 SaaS 的个人职责、上线范围及“200+ 家酒店”的统计时点需能说明。

三、Agent、LangGraph 与工具调用

07. 工作流和 Agent 有什么区别？【P0】

参考回答： 工作流主要由开发者定义步骤和分支，Agent 允许模型根据上下文选择行动。我的 mate-assist 是业务约束下的图编排，意图路由和检索重试发生在有限范围内。

在 Web3 场景，行情查询、指标计算和权限校验用确定性代码；复杂问题拆解和证据组织交给模型。模型自主性应与任务的不确定性匹配。

追问： 固定报表是否需要 Agent？通常先用普通任务和模板，确有动态分析需求再引入。

08. LangChain、LangGraph、LlamaIndex 如何分工？【P0】

参考回答： LangChain 提供常用模型与工具集成，LangGraph 适合显式状态和复杂控制流，LlamaIndex 更贴近数据索引与检索应用。我在不同项目使用这些能力，但不会为了覆盖技术栈把三个框架都强制引入。

框架应被封装在适配层，业务服务依赖稳定接口。先说明需求，再说明选型；不同版本有功能重叠，不能将它们讲成互斥产品。

09. 一个 Tool Calling 请求如何安全执行？【P0】

参考回答： 模型产生工具名和参数，服务端完成 Schema 校验、身份验证、资源权限检查与业务约束，再执行工具并回传结构化结果。Schema 合法不代表业务授权成立。

结合 Registry 的经验，我会在工具入口验证用户、租户和资源关系。钱包地址、链 ID、查询时间范围也都要验证，并在结果中带上数据时间和来源。

追问： 模型传入 user_id 能否作为身份？不能，可信身份来自认证上下文。

10. 如何设计好的工具 Schema？【P1】

参考回答： 名称和描述要明确动作与适用范围，参数使用受约束类型，规定单位、时区、链 ID 和最大查询范围。工具尽量对应明确的业务动作，避免万能的 execute_anything。

返回值区分成功、无数据、数据过期、权限不足和上游故障，并包含可追踪的资源 ID。可以用 JSON Schema 做结构约束，用业务代码处理跨字段约束。

追问： 工具太多怎么办？按任务与权限先筛选候选工具，避免把整个注册中心一次性塞给模型。

11. ReAct、Plan-and-Execute 和固定图怎么选？【P1】

参考回答： ReAct 适合根据观察逐步决定行动；Plan-and-Execute 先规划再执行，适合较长任务，但计划需要修订；固定图最便于控制和审计。

我会先用固定图限定业务边界，在需要探索的局部使用有限循环。计划只是执行建议，每一步仍要做权限、预算和结果检查。

追问： 不需要保存或展示模型隐藏推理；保存工具选择、执行结果和简洁决策摘要即可支持审计。

12. 如何防止 Agent 死循环？【P0】

参考回答： 设置总时间、最大步数、工具调用数和成本预算，记录重复的工具参数与无新增证据次数。成功、无答案、需澄清和依赖失败都要有明确出口。

mate-assist 有低质量结果重写重检索分支，面试时应解释它的真实停止条件。不要只回答框架有 recursion limit，那只是最后一道保护。

13. Checkpointer、Store 和业务数据库有什么区别？【P0】

参考回答： Checkpointer 保存执行状态，Store 用于跨执行访问的记忆或数据，业务数据库保存订单、审批等权威记录。我的项目使用 MySQL Checkpointer / Store，但它们不能自动替代业务事务。

thread_id 用于定位执行上下文，不等于用户身份。读取线程或记忆之前仍要校验租户和归属。官方机制说明见LangGraph Persistence。

14. 节点恢复会不会重复执行？【P0】

参考回答： 需要假设恢复过程中可能重放部分代码，所以有副作用的操作必须幂等。状态恢复解决“从哪里继续”，执行记录解决“是否已经做过”。

比如工具创建外部任务后本地写入失败，恢复时先用业务幂等键查外部任务。外部服务不支持幂等或查询时，不能保证自动恢复绝不重复，应进入结果未知状态并对账。

追问： 不要把持久化框架宣传成外部操作 exactly-once 保证。

15. 人工审批和 interrupt 怎么设计？【P0】

参考回答： 需要审批时持久化操作摘要并暂停，审批绑定目标、参数、有效期和版本。恢复执行前重新验证权限、额度和数据时效，参数变化则重新审批。

尤其要留意恢复时节点可能重新开始执行，审批节点之前的副作用需要幂等。框架暂停机制参考LangGraph Interrupts。这部分是设计回答，不暗示我已经实现过 Web3 交易审批。

16. 对话记忆怎样防止串用户或污染？【P0】

参考回答： 对话状态与长期记忆分开，以租户、用户、会话和用途组织访问范围。长期记忆保存必要事实，带来源、更新时间、置信状态和删除机制，不直接永久保存全部聊天。

mate-assist 包含记忆抽取和跨会话持久化。我会说明真实抽取规则；对矛盾信息、用户纠正和敏感内容，应有更新、失效或不写入策略，避免一次错误成为后续所有回答的前提。

17. SSE 断开与用户中断有什么区别？【P0】

参考回答： SSE 断开是连接状态，用户中断是业务动作。断开后任务是否继续取决于产品设计，不能把二者直接等同。

我做过 SSE 与用户中断，会按真实实现说明取消信号如何传到节点、是否能够取消上游请求，以及如何保存部分结果。不可取消的外部操作仍需记录最终状态；界面停止显示不代表后台已经停止。

18. 什么时候使用多 Agent？【P1】

参考回答： 当任务可以按领域、上下文或权限独立拆分，并且协调成本低于收益时才使用。市场规则、数据分析和报告核查可以分工，但读取三个 API 通常直接并发调用更简单。

先建立单 Agent 评测基线，再比较质量、成本和耗时。多个模型意见一致不等于事实正确，最终仍依赖外部证据。

19. MCP 与 Tool Calling、A2A 的区别？【P0】

参考回答： Tool Calling 是模型提出工具调用的机制；MCP 规范客户端与服务器之间的工具、资源等交互；A2A 面向 Agent 之间的任务协作。它们解决不同层面的问题。

我的 Registry 经历可以用于说明统一接入和工具发现。MCP 不是业务权限系统，不会天然保证工具安全，也不是所有工具调用都必须使用的协议。

20. 如何管理 Prompt 版本和回滚？【P0】

参考回答： mate-assist 将 50+ 运行时 Prompt 从镜像解耦，使用 manifest、变量和必含段校验作为 CI 门禁，通过不可变 release tag 与启动校验管理版本。

一次运行要记录模型、Prompt、工作流和检索配置版本，出现回归才有条件定位与回滚。回滚 Prompt 只能影响后续执行，不能撤销已经发送的通知或交易。

追问： 结构校验能发现缺变量，发现不了语义退化，仍需离线评测与灰度观察。

四、RAG 与数据工程

21. Web3 RAG 应存什么，实时数据怎么处理？【P0】

参考回答： 协议文档、市场规则和产品 FAQ 适合知识库；价格、订单簿、余额与交易状态通过实时工具查询。回答时明确文档版本和数据时间。

我可以迁移企业 RAG 的接入与检索能力，但不会将高频行情持续向量化当作权威查询方式。静态知识解释“规则是什么”，动态数据回答“现在发生什么”。

22. 如何切分 PDF、表格和多模态文档？【P1】

参考回答： 我做过 PDF、Word、PPT、Excel、邮件和图片的处理。切分首先保留标题层级、表格表头、页码和附件关系，再根据检索需要调整粒度。

大表可以按逻辑区域切分并重复必要表头，图片提取结果保留原图引用。不能只按固定字符数切，否则规则条件和例外条款可能被拆开。OCR 结果也需要置信与来源，不应默认无误。

23. BM25、向量检索、混合检索怎么选？【P0】

参考回答： BM25 擅长关键词与特定术语，向量检索擅长语义表达差异。混合召回后可以用 RRF 等方式融合，避免直接相加不可比的分数。

我有 Weaviate 与 metadata filtering 的实践。合约地址、交易哈希和市场 ID 优先精确查询，再用语义检索补充背景。混合检索是否更好，要用目标问题集验证。

24. Reranker 有什么价值和代价？【P1】

参考回答： Reranker 对查询与候选证据的匹配关系重新排序，适合改善召回候选较多但排名不理想的问题。它不能找回根本没有召回的文档。

我会先测候选集召回率，再比较重排后的排序指标、最终回答和额外延迟。高风险规则问答可给更多预算，简单精确查找可以跳过。

25. Query Rewrite 会不会把问题改错？【P0】

参考回答： 会，所以要保留原问题与结构化实体，约束改写不能改变金额、时间、否定词和市场标识。多轮对话补全指代时，也要识别歧义并允许澄清。

我做过 Query Rewrite，会准备真实的输入输出案例。建议用原查询与改写查询并行召回后合并，并记录改写对召回的实际增益；不要把所有问题都无条件改写。

26. RAG 效果差如何定位？【P0】

参考回答： 依次检查资料是否存在、解析是否正确、切分是否完整、过滤是否过严、召回是否命中、重排是否保留、生成是否忠于证据。每层都有独立样本与指标。

企业 RAG 经历适合回答这题，但要选择真实发生的问题说明。如果没有现成事故记录，就讲排查方法，不编造“上线后曾发生”的故事。

27. 多租户知识库怎么做权限过滤？【P0】

参考回答： 请求身份来自认证链路，授权过滤条件由服务端生成，向量、关键词和缓存路径都必须遵守。检索候选进入模型之前就应符合权限，读取原文和附件时再次验证。

我做过数据源级权限过滤与 Registry 对象 ACL。权限发生撤销时，需要同步处理索引元数据和缓存失效；不能只在回答生成后隐藏引用，因为内容已经进入上下文。

28. 文档增量同步如何去重与删除？【P0】

参考回答： 我做过全量、增量、定时和事件驱动连接器。记录外部文档 ID、版本、内容哈希和同步游标，内容不变时避免重复解析与 Embedding。

更新需要关联旧 chunk，删除需要清理索引与缓存，游标推进应与处理结果保持一致。Webhook 用于及时通知，周期性校验用于修复漏通知。同步的分钟级改善与处理效率提升，应分别解释测量口径。

29. Embedding 模型升级怎么做？【P1】

参考回答： 不直接混用不同模型生成的向量，即使维度相同，空间也未必兼容。为新模型建立版本化索引，重新向量化并评测召回与延迟，切换时保留回滚条件。

文档、chunk、Embedding 模型和索引版本需要关联。对于增量写入，明确新旧索引的写入策略与切换窗口。这是推荐方案，不能声称过去已经采用过完整双索引迁移。

30. RAG、微调、长上下文怎么选？【P1】

参考回答： 可更新事实与可追溯知识优先 RAG；稳定的格式、语气或特定任务行为可以考虑微调；少量完整资料可直接放长上下文。

长上下文不等于模型一定能找到关键事实，微调也不适合保存持续变化的行情。先定义问题属于知识缺失、检索失败还是行为不稳定，再选方案。

31. 你怎么做评测，如何证明不是 Demo？【P0】

参考回答： 固定一组有代表性的用户任务，覆盖正常、歧义、无答案、旧资料、上游失败和权限问题。分别评估召回、证据支持、工具参数正确性、任务完成率、P95 时延和单任务费用。

数值计算和权限用确定性断言，开放式回答结合人工标注与模型辅助评审，并校验评审一致性。离线评测通过后，再观察真实流量的失败类型。没有测过的准确率不填数字。

五、Python、Go 与分布式后端

32. FastAPI 的 async 为什么仍可能阻塞？【P0】

参考回答： async def 内调用同步网络 SDK、阻塞 ORM 或大规模 CPU 计算仍会占住事件循环。使用异步客户端与连接池，将阻塞 I/O 放受控线程池，CPU 重任务交独立进程或 Worker。

我有 FastAPI 和多数据源调用经验，会从事件循环延迟、依赖耗时、线程池等待和连接池饱和定位。框架不会自动把异步函数里的所有代码变成非阻塞。

33. GIL、线程、进程和协程怎么回答？【P1】

参考回答： 对常见启用 GIL 的 CPython 构建，纯 Python CPU 任务不能仅靠多线程获得理想的多核并行；I/O 等待可以用线程或协程提高并发，CPU 任务可用多进程或释放 GIL 的原生库。

不能把“Python 永远有 GIL”当成绝对结论，应先明确解释器和构建。工程上先判断任务瓶颈，再决定并发模型，并控制任务数量和内存。

34. 如何做有界并发、超时与取消？【P0】

参考回答： 给整轮任务设置总截止时间，子调用使用剩余预算，并通过 Semaphore 或有界队列限制并发。不能为一万条记录直接创建一万个无约束请求。

取消后释放连接与资源，不吞掉取消信号；并发任务按业务决定失败时取消其他分支还是返回部分结果。重试时间也应计入总预算。

35. FastAPI、Django 怎样选？【P1】

参考回答： Agent API、流式输出和异步服务通常适合 FastAPI；如果项目需要成熟的管理后台、ORM 和标准业务 CRUD，Django 也很合适。

我用过 Django、Flask 和 FastAPI，选择主要看现有团队、业务复杂度与依赖。不要只用框架基准测试决定选型，数据库和外部模型往往才是主要耗时。

36. 为什么长任务不用 BackgroundTasks？【P0】

参考回答： 轻量响应后操作可以使用 BackgroundTasks，但长时间文档处理或 Agent 分析需要持久化任务、独立 Worker、重试和状态查询，我会用 Celery 等队列体系。

我做过 Celery / SQS 与离线分析任务。API 返回任务 ID，执行状态单独持久化；进程重启后不能依赖内存中的后台任务继续存在。FastAPI 官方说明

37. Celery 如何保证任务不重复？【P0】

参考回答： 我不会承诺消息系统保证业务绝不重复，而是用幂等任务适应重复投递。业务键建立唯一约束，状态转换使用事务，外部操作携带幂等键。

acks_late 改变确认时机，不提供 exactly-once；进程退出和 broker 行为还受配置影响。瞬时错误才重试，永久错误进入失败处理。Celery 官方 Tasks 文档

38. 如何解决数据库写入成功但 MQ 发布失败？【P0】

参考回答： 可以使用 Transactional Outbox，在同一个数据库事务中写业务记录与待发布事件，再由独立发布器投递。发布器可能重复发送，所以消费者仍需幂等。

这能避免业务提交后消息永久遗漏，但不是跨数据库和 MQ 的原子事务。需要监控积压、失败次数和最老事件年龄，并定义补偿路径。

39. Redis 缓存和锁怎么用？【P1】

参考回答： 缓存键包含租户、权限版本、查询参数和数据版本；TTL 根据实时性要求设置。热点使用请求合并，TTL 可加抖动，空结果短缓存避免穿透。

锁要有唯一持有者标识并原子校验后释放，但租约过期后旧 Worker 可能继续运行。涉及重要写入时，用数据库约束、版本号或 fencing token 保护资源，不能认为拿到 Redis 锁就绝对安全。

40. 如何排查慢 SQL、设计索引和分页？【P0】

参考回答： 我有业务接口与 SQL 优化经历。先用慢查询日志和执行计划定位扫描行数、连接方式、排序与锁等待，再根据过滤、排序和选择性设计索引，而不是给每列都建索引。

长列表使用稳定排序和游标分页，例如按时间加唯一 ID；深 OFFSET 会增加扫描成本。写入成本、索引空间和 N+1 查询也要一起评估。简历中响应时间从 2.5 秒到 0.8 秒以内，需要说明是在什么接口与负载下测得。

41. 如何防止重复订单或并发超额操作？【P0】

参考回答： 幂等请求键用数据库唯一约束落地，状态变化用条件更新或合适的锁与事务。例如只允许从待处理改成执行中，检查受影响行数。

不要先查询“是否存在”再无保护地插入。外部执行与本地事务之间仍有不确定窗口，需要外部操作 ID、对账和结果未知状态，而不是不断重试创建新订单。

42. SSE、WebSocket 和普通轮询怎么选？【P1】

参考回答： 单向输出文本和任务进度用 SSE 比较直接；频繁双向交互可考虑 WebSocket；简单任务状态也可以轮询。恢复连接依赖事件序号和服务端保留记录，不是换协议就自动可靠。

SSE 还需要考虑代理缓冲、空闲超时、心跳和背压。我的经验可以从首字输出、整轮耗时和用户中断讲起。

43. Go 的 GMP、channel、context 会怎么问？【P1】

参考回答： G 是 goroutine，M 是操作系统线程，P 是调度所需的执行资源。阻塞系统调用时运行时可以让其他线程继续执行可运行任务，但具体调度细节应结合 Go 版本。

channel 用于通信与同步，并不意味着不需要锁；context 用于截止时间、取消和请求范围信息，取消是协作式的。要能解释向已关闭 channel 发送会 panic、nil channel 的收发会阻塞，以及 goroutine 泄漏如何发生。

背景表达： 我的生产主线是 Python，Go 按实际熟悉程度回答。深入复习已有Go 常见面试题，不要编造 Go 项目规模。

44. Python 和 Go 如何分工，何时拆微服务？【P1】

参考回答： 初期优先 Python 完成数据与 Agent 闭环；对经测量确认的高并发采集、连接管理或计算瓶颈，再评估 Go 模块。先考虑优化算法、批处理和 I/O，不把换语言当成万能性能方案。

拆服务的依据是独立扩缩容、发布节奏和职责边界。跨服务会增加重试、追踪、版本兼容和数据一致性成本，早期模块化单体可能更合适。

六、Web3 业务与链上数据

45. Polymarket 的数据怎么接入？【P0】

参考回答： 我会把市场元数据、订单簿行情、用户活动与链上结算分开接入。Gamma 面向市场和事件元数据，CLOB 相关接口提供订单簿、价格与交易能力，Data API 覆盖持仓和成交等信息。

内部映射 event、market、condition 与 outcome token 等标识，不仅靠标题关联。每条数据保留来源与时间；链下订单簿不能仅靠链上事件完整还原。Polymarket 数据概览

46. 怎样解释预测市场价格？【P0】

参考回答： 市场价格可以作为市场参与者对结果的定价信号，但不是客观真实概率。展示时必须区分最新成交、买一、卖一和中间价；薄流动性下，它们可能差异明显。

对于“为什么变化”，我先报告可核验的变化，再列出有来源的可能解释，不能把同时发生的新闻直接断言为因果。还需要阅读结算条件，避免比较表面相似但定义不同的市场。

47. 链上索引服务怎么设计？【P0】

参考回答： 用历史回填加增量同步，按链和区块范围查询日志，记录游标、区块哈希及解析版本。WebSocket 用于低延迟，RPC 范围查询用于补漏与核对。

我已有多源增量同步经验，但链上需要额外处理最终性和重组。分块大小根据节点限流与结果数量调整，监控距链头延迟，游标只推进到完整处理的连续区间。RPC 能力参考Ethereum JSON-RPC。

48. 重组、最终性与事件去重如何处理？【P0】

参考回答： 保存区块父子关系及事件归属，区分观察到、已确认与最终确定等状态，确认策略按具体链配置。发生重组后定位共同祖先，撤销旧分支派生数据并重放新分支。

单次日志出现可用链 ID、区块哈希、交易哈希和日志索引标识，同时维护 canonical 状态。仅使用交易哈希去重不够，一笔交易有多个日志，交易也可能在重组后重新入块。下游聚合应支持重算或可追踪撤销。

49. 如何理解 ABI、event 与历史合约状态？【P1】

参考回答： ABI 描述编码与解码规则，日志包含地址、topics 和 data。解析事件需要匹配对应合约及版本，不能把所有日志都按一个事件结构解码。

代理升级可能导致同一地址对应不同实现，需要按区块关联版本。读取历史状态还依赖节点能力，不是普通 RPC 服务一定保留所有历史状态。优先保留原始数据，便于修复解析器后重放。

50. 金额精度、余额与 PnL 怎么算？【P0】

参考回答： 资产数量保留最小单位整数及 decimals，展示和估值使用明确精度与舍入规则，避免二进制浮点误差。价值计算还要指定报价币种和价格时间。

PnL 必须先定义已实现、未实现、手续费、转入转出和成本基础，不能简单用当前余额减充值额。在 Agent 中，计算由代码完成，模型负责解释口径和结果。未拿到完整历史时，应明确估算边界。

51. DeFi、NFT、GameFi 会问哪些数据问题？【P1】

参考回答： DeFi 需要理解 AMM、借贷与清算等业务，TVL 与收益率必须有协议范围和时间口径；NFT 要区分 Token ID、所有权、授权与外部元数据，地板价并不等于每个 NFT 的成交价值；GameFi 要区分钱包、真实用户、机器人和游戏内行为。

这些指标都涉及数据质量、重复地址、估值与口径，不能把链上交易数直接等同于活跃用户。具体协议的参数与风险规则必须以对应文档和合约为准；这里不假设我有相关生产项目经历。

52. RPC 返回不同结果或供应商宕机怎么办？【P1】

参考回答： 比较是否查询同一网络、区块高度和区块哈希，区分链头延迟、缓存、节点能力和真实分叉。关键查询尽量固定区块快照，而不是混用不同时间的 latest。

设置超时、熔断、限流和有限故障切换，记录来源变化。多供应商一致也不是绝对正确性证明，最终要结合规范链与业务确认规则。降级时标注数据时间，不让模型补出实时数据。

53. Agent 发交易如何防止重复扣款？【P0】

参考回答： 模型只产生交易意图，服务端执行校验、审批、构造与受控签名，私钥不进入模型上下文。持久化 intent ID、链、发送者、nonce、交易哈希与状态。

超时后先核查已有交易和 nonce，不直接创建新业务操作。某些情况下可以重播相同签名交易，但交易替换、丢弃和重组需要按链规则处理。签名服务不支持查询与幂等时，必须承认结果不确定的边界。

追问： 模拟成功不保证执行成功，状态和价格可能变化。审批、额度和费用上限仍要在执行时校验。

七、安全、部署与故障排查

54. OAuth、OIDC、JWT、RBAC、ACL 如何区分？【P0】

参考回答： OAuth 解决授权委托，OIDC 提供身份层，JWT 是令牌表示格式，RBAC 按角色授权，ACL 对具体对象授权。验签之外还检查发行者、受众、过期时间与必要声明。

结合 Registry，我会解释网关身份与下游授权如何分离。给 MCP Server 的令牌不能随意透传给另一资源服务；下游使用适用的凭据与权限。MCP 授权规范，2025-06-18 版本

55. 如何防 Prompt Injection、SSRF 和数据泄露？【P0】

参考回答： 检索结果与工具文本都作为不可信数据，不允许其中的指令扩大工具权限。网页读取限制协议、目标与重定向，并在连接前处理内网地址和 DNS 变化风险。

敏感日志按字段脱敏，Trace 控制内容采集和访问权限。模型上下文不放密钥，工具按最小权限划分。只读分析流程没有签名权限，比单纯依赖提示词更可靠。

56. Kubernetes、KEDA 和模型限流怎么配合？【P0】

参考回答： 我的离线任务使用 KEDA 根据 Redis 队列积压在 0–10 副本间伸缩，但副本增加不能突破模型服务的总额度。应同时控制全局请求率、Token 预算与并发，避免所有 Worker 同时重试。

部署还要考虑优雅停机、在途任务、可见性超时与冷启动。上线前检查资源请求、健康检查和队列最长等待；不能只以 CPU 使用率判断 Agent 服务健康。

57. 如何优化和观测延迟、费用、故障？【P0】

参考回答： 我做过首字、整轮和节点 Trace，会拆出排队、检索、重排、工具、模型首 Token 与生成耗时。费用按模型、输入输出量和任务汇总，失败按依赖与节点归因。

先找主要耗时，再减少模型轮次、并发独立查询、缩短上下文或缓存稳定结果；对权限与实时行情谨慎缓存。每次优化同时回归质量，平均值改善不能掩盖 P95 恶化。

八、综合设计、行为面试与反问

58. 两周做出 Polymarket 分析 Agent，怎么安排？【P0】

参考回答： 我会将目标限定为“输入市场链接或问题，返回规则、行情变化和证据”，先验证只读闭环。两周是计划假设，依赖接口权限、团队支持和范围稳定。

第 3–5 天 数据适配器、规则知识库与基础工作流 关键数字来自结构化工具，引用可访问
第 6–8 天 状态持久化、SSE、限流、错误和恢复 重启、超时、无数据与断线可解释

用户请求 → 认证与任务创建 → 市场实体解析 → 歧义澄清
                                      ↓

                                      ↓
                         证据与时间一致性检查
                                      ↓
                         确定性指标计算 → 报告生成
                                      ↓
                         关键字段核验 → SSE / 最终结果

任务状态至少包含 pending、running、waiting_input、succeeded、failed、cancelled；交易场景另设业务状态机。建议数据对象包括任务、执行事件、市场映射、行情快照、证据引用和工具执行记录。

验收案例： 同名市场、已关闭市场、规则更新、接口限流、返回空数据、行情过期、重复请求、越权访问、执行中重启。阈值由业务协商，不虚构已经达到的准确率或并发量。

60. 你有什么问题想问我们？【P0】

参考回答： 我希望了解当前最优先解决的用户任务，以及第一个月期待我交付什么结果。Agent 是提供只读分析、运营辅助，还是会触及订单和钱包执行？现有链上索引、模型接入和知识库有哪些基础？

进一步询问产品、后端、合约和运维如何分工，成功率、延迟与费用由谁定义，是否已有真实用户和反馈。对于持续建设中的团队，还应确认代码所有权、上线流程和技术决策机制。

这些问题用于判断实际职责和交付条件，不根据 JD 推断公司已经具备某种基础设施。

61. Agent 的 P95 从 8 秒涨到 30 秒，你怎么排查？【P0】

先澄清： 是首字延迟还是整轮耗时？哪些任务、租户和发布时间开始变慢？错误率、输入长度和模型调用轮数是否同步变化？

参考回答： 我会先按任务类型和版本对比 Trace，把排队、检索、重排、工具、首 Token 和生成时间拆开。均值不变而 P95 上升，可能是长尾依赖或排队；首字正常但整轮变慢，则重点看输出长度、追加工具调用和客户端消费速度。

如果与发布高度相关，先灰度回退降低影响，再定位具体节点。上游变慢时，设置整轮截止时间和有限并发，优先保留核心数据查询，取消非必要补充查询。不能只增加 Worker，否则可能把模型限流和数据库等待进一步放大。

取舍与验证： 比较同类请求的 P50/P95/P99、队列等待和任务完成率；用代表性问题回归答案质量。模型首 Token 到达与用户实际看到首字是不同指标，要检查代理缓冲。

我的经历切入： mate-assist 已有首字、整轮和节点 Trace，可以说明真实采集位置；不要把本题的 8 秒、30 秒说成项目数据。

62. 热点事件带来十倍请求，扩容后仍大量 429，怎么办？【P0】

先澄清： 上游限制的是 RPM、TPM 还是并发？是否多个服务共享同一额度？哪些请求可延迟、合并或降级？

参考回答： 扩容只增加执行能力，不增加上游额度。我会在调用入口建立共享预算与有界队列，按租户或业务优先级分配容量。热点只读查询可以合并相同请求，但权限和行情时间范围必须一致。

收到 429 后根据服务端提示进行有限退避并加入抖动，不让每个 Worker 各自高频重试。队列满时明确拒绝或返回排队状态，限制最长等待，避免系统表面接收成功却永远无法完成。

取舍与验证： 公平性与整体吞吐可能冲突；交互请求和离线分析应分配独立预算。压测检查上游调用率、排队时长、拒绝率和恢复过程，不只看 Pod 数量。

我的经历切入： Celery、并发闸门和 KEDA；明确分布式限流属于要按实际实现补充的部分。

63. 一个大客户耗尽预算，其他客户无法使用，怎么设计？【P0】

先澄清： 限制是按用户、租户、套餐还是项目？超额后拒绝、降级还是允许付费继续？运行中的任务是否应完成？

参考回答： 先认证，再确定可信租户与预算桶；同时限制请求数、并发和模型消耗。执行前预留预算，执行后按实际用量结算，长任务每个阶段都检查剩余预算。预算预留需要原子更新，避免并发请求全部判断余额充足。

异常退出后通过任务状态和对账回收未使用预留；如果上游已经计费但本地未收到用量，保留估计与待核对状态，而不是立即把全部预算释放。缓存和共享结果也不能跨权限边界。

取舍与验证： 精确计费与实时限制是两套相关机制；用并发超额、Worker 崩溃和重复结算测试保证不重复扣减。这里的预算控制指系统资源与费用额度，并不代表已有商业计费系统经历。

64. 工具已经发出通知，写 Checkpoint 前进程崩溃，恢复会重发吗？【P0】

先澄清： 外部服务是否支持幂等键、查询执行结果或回执？通知是否允许重复？

参考回答： 我会把业务动作标识在调用前持久化，并把相同标识传给支持幂等的外部服务。恢复时查询已有动作结果，成功则复用，不再创建新动作。操作记录的状态至少区分准备、执行中、成功、失败和结果未知。

如果外部服务既不支持幂等也无法查询，崩溃窗口中无法同时保证不丢失和不重复。这时要按业务选择人工核对、允许重复并做内容去重，或改用支持幂等的服务，不能承诺 Checkpointer 自动解决。

取舍与验证： 注入“远端成功、本地落库前崩溃”，恢复后核对外部动作数量，而不是只检查本地任务显示成功。

我的经历切入： Agent 恢复与 Celery 任务经验。先说恢复能力，再说明副作用的额外要求。

65. 同一会话两个请求同时运行，历史记录相互覆盖怎么办？【P0】

先澄清： 产品允许同会话并行分支吗？第二次请求是追加、编辑还是重生成？

参考回答： 默认对同一会话的状态修改串行化，入口用数据库状态或版本控制建立运行约束，不能仅依靠单进程锁。允许并行时，为每个 run 建独立分支与父版本，完成后按明确规则合并，拒绝把旧版本结果覆盖到新会话。

用户编辑后重生成应从指定消息版本开始，原分支保留可追踪标识。长期记忆写入也需要验证结果是否仍属于有效分支，避免被取消的旧回答污染记忆。

取舍与验证： 串行更简单但可能等待；分支体验更灵活但状态管理更复杂。测试双请求、乱序完成、重复提交和编辑后旧任务返回。

我的经历切入： mate-assist 的回溯与删除重生成，具体并发策略按真实实现说明。

66. 用户点击停止后仍在扣费，而且刷新页面又显示旧回答，怎么办？【P0】

先澄清： 停止仅停止展示，还是取消整个任务？上游 API 是否支持取消，任务是否已进入不可逆工具执行？

参考回答： 将取消请求持久化，并传到运行任务；各节点在进入昂贵操作前检查取消状态。向上游传播取消信号，停止新的调用，但不能承诺已经完成或不可取消的请求不计费。

服务端结果写入要验证 run 是否仍有效，取消后的迟到结果不能成为当前会话答案。客户端通过 run ID 和事件序号区分旧流与新流，刷新后查询权威任务状态，不能从内存缓存猜测。

取舍与验证： 检查停止到实际停止的时间、停止后新增调用次数和迟到结果隔离。涉及不可逆动作时，停止应转为状态查询和结果告知。

67. 检索命中了正确文档，模型仍给出错误答案，怎么修？【P0】

先澄清： 正确证据是否实际进入最终上下文？有没有旧版本、相反条款或问题中的否定条件？

参考回答： 先保留最终送入模型的证据，而不是只看检索 Top K。可能是重排、截断、上下文组织或多个版本冲突。对金额、期限等关键字段，用结构化抽取或代码核验，要求结论关联具体证据片段。

如果证据矛盾或缺少决定条件，返回冲突和待确认信息。降低温度、加一句“不要幻觉”可以作为调整，但不能代替证据与字段校验。

取舍与验证： 为这个错误建立最小复现及相似反例，包括改写问题、否定条件和旧版本干扰，验证修复不会只对单题有效。

我的经历切入： RAG 检索评分、重写重检索与引用回传。证据已正确时，不盲目增加检索轮数。

68. 用户被撤销权限，但 Agent 仍从缓存回答旧文档，怎么办？【P0】

先澄清： 权限来源和撤销事件是否可靠？泄露来自检索缓存、答案缓存、历史对话还是长期记忆？

参考回答： 先阻止继续提供受影响内容，再按链路清查缓存与历史上下文。缓存键纳入授权范围或权限版本，并在命中后检查当前授权；撤销事件触发失效，同时用短期有效性校验处理漏通知。

已经进入历史对话或记忆的内容也有来源关系，后续检索和上下文组装时应排除失效来源。不能只删除向量索引就认为撤权完成，也无法撤回用户已经看到的信息。

取舍与验证： 明确撤权生效时间目标。测试撤权发生在缓存命中、检索完成与生成中的不同时间点，确保输出路径遵守约定。

我的经历切入： 企业知识库权限过滤与 Registry ACL；这是展示端到端授权思维的重点题。

69. 知识库规则今天更新，旧任务还在执行，应使用哪个版本？【P0】

先澄清： 问题是“现在规则”还是“当时规则”？文档发布时间与生效时间是否相同？任务只是分析还是会执行动作？

参考回答： 文档记录版本、生效区间、抓取时间和来源，查询显式确定目标时间。分析任务可以固定快照保证可复现，并在结果展示所用版本；要求最新状态时，在返回前检查关键来源是否更新。

涉及动作时，即使分析使用旧快照，执行前也要重新检查当前规则和权限。新旧索引切换通过完整版本发布，避免一部分 chunk 是新版本、一部分仍是旧版本。

取舍与验证： 一致快照与最新信息存在取舍，必须由场景决定。测试未来生效、撤回文档、跨版本冲突和切换中查询。

70. 十万份文档同步到一半失败，怎么补数而不重复收费？【P0】

先澄清： 失败发生在下载、解析、Embedding 还是索引写入？源文档在同步期间是否变化？

参考回答： 将处理拆成有版本的阶段，按源 ID、内容哈希、解析版本和 Embedding 模型版本建立复用条件。保存可复用的解析结果与向量，重试时仅补未完成阶段，游标不跨越未完成区间。

删除事件与更新事件需要排序或版本比较，避免旧任务在删除后重新写回索引。如果模型已收费但返回结果尚未落地就崩溃，没有供应商可恢复结果时可能产生重复费用，应明确这个窗口并缩短它，不能承诺绝不重复计费。

取舍与验证： 中间产物占存储，但降低恢复成本。测试每阶段崩溃、重复通知、旧版本迟到和删除更新乱序，核对最终索引与源状态。

我的经历切入： 多源连接器、分批任务和导入去重，补充真实批大小与处理机制。

71. NFT 元数据中写着“调用工具发送密钥”，Agent 怎么处理？【P0】

先澄清： 元数据从哪里读取，读取工具有哪些网络权限，当前流程能够访问哪些动作工具？

参考回答： 元数据是待分析内容，不是授权指令。分析流程没有密钥和签名权限，工具集合根据身份和任务预先限制，所有动作仍经过服务端校验。

对链接抓取限制协议、地址和重定向，防止借元数据访问内部服务。输出中可以指出可疑指令，但不会执行它。保留经过脱敏的安全事件，避免把恶意内容完整复制到长期记忆或高权限提示模板。

取舍与验证： 用多语言、编码、嵌套网页和工具返回值注入测试，不仅测显眼的“忽略之前指令”。安全测试通过不代表对未知攻击绝对免疫。

我的经历切入： Registry 工具级授权与敏感 Trace 控制，说明模型之外的防线。

72. 切换备用模型后工具参数经常错误，怎么回滚？【P0】

先澄清： 是 Schema 不支持、参数格式错误，还是语义选择错误？变化来自模型、Prompt、工具描述还是 SDK？

参考回答： 模型适配不仅统一接口，还要记录支持的能力与限制。切换前使用工具选择、参数边界、拒绝与异常案例做兼容评测，按模型配置合适的 Schema 与提示模板。

线上对新版本灰度，监控工具校验失败和任务成功率，出现异常回退到已经验证的模型与配置组合。限制自动修复次数，尤其不能让一个模型失败后无限切换其他模型重复执行有副作用工具。

取舍与验证： 备用模型不一定具备相同能力；无法安全完成时明确降级。回滚后固定相同评测集比较，并检查在途任务使用哪个配置版本。

我的经历切入： 多模型接入、Prompt manifest 和不可变版本；没有测过的模型组合不声称兼容。

73. 链重组后报表重复累计成交量，怎样修复？【P0】

先澄清： 原始日志是否保留区块哈希？派生报表是否记录输入事件？错误范围能否定位到具体链和区块？

参考回答： 暂停受影响聚合的推进，找到共同祖先并标记旧分支事件非规范。按规范链重新计算受影响区间，重建报表版本后切换读取，并保留修正记录。

线性可加指标可以做受控撤销，但去重用户数、排名等非线性指标不能简单减回一笔。优先建立可重放的原始事件层，游标、解析版本与报表版本关联。

取舍与验证： 重算耗时但语义清晰；直接补丁修改快但容易遗留错误。用不同深度的模拟重组和交易重新入块验证聚合与全量重算一致。

我的经历切入： 增量同步与幂等可迁移；明确没有把该案例描述为实际链上事故。

74. 行情 WebSocket 断线五分钟，重连后能直接继续用吗？【P0】

先澄清： 数据源提供完整快照还是增量？是否有序列号、重放接口或校验机制？必须查具体协议，不能假设存在这些能力。

参考回答： 断线期间将行情标记为过期，停止输出依赖完整订单簿的实时结论。重连后按供应商协议重建快照与增量衔接，若有序列号则检测缺口和乱序；无法证明连续性就重新建立状态。

保存来源时间和本地接收时间，防止旧消息覆盖新快照。不能只因为连接恢复就把数据标记为正常，也不能将链上成交日志当作完整订单簿补丁。

取舍与验证： 全量重建增加带宽，但优于使用已损坏状态。故障测试包含漏消息、重复、乱序、重连和快照获取期间的新消息。

75. 提交交易超时，用户又点了一次，怎么回答与处理？【P0】

先澄清： 交易是否已签名，是否已知交易哈希，是否发送给网络？第二次点击是相同意图还是新操作？

参考回答： 同一业务意图使用稳定幂等键，重复点击返回已有操作状态。超时意味着结果未知，先查询已有交易、回执与发送账户状态，再决定继续等待、重播同一交易或进入受控替换流程。

不要只凭 pending nonce 就断言成功，它可能受到其他交易影响。费用、nonce 分配与替换关系由签名执行层管理，大模型不能自行修改金额、收款地址或重新创建业务意图。

取舍与验证： 宁可让用户看到“正在核实”，也不能用猜测的成功或失败诱发重复操作。模拟远端接收后断网、重复点击、替换交易和重组，核对真实执行次数。

76. 用户问“这个市场为什么突然涨了”，Agent 怎样避免胡编？【P0】

先澄清： 哪个结果 Token、哪段时间、比较成交价还是盘口？涨幅的基准和最低流动性条件是什么？

参考回答： 先确认涨幅确实存在，检查稀疏成交、价差扩大或市场映射错误。再查询对应时间范围的规则变更与可靠事件来源，报告可核实的变化。

将答案分成事实、可能解释和信息缺口。新闻在时间上相近只能支持关联线索，不能直接证明因果；证据不足就说无法确认原因。把“价格上涨”与“事件真实概率提高”明确区分。

取舍与验证： 输出可能比确定性的叙事克制，但更可信。评测包含无新闻上涨、单笔异常成交、旧新闻重发和相似市场混淆。

我的经历切入： 企业 RAG 引用与 Agent 证据检查；这是业务分析能力而非投资推荐。

77. 用户要求监控钱包异动，如何减少误报和通知轰炸？【P1】

先澄清： 监控转账、授权、持仓变化还是协议交互？阈值按数量还是估值？需要多快，允许多少未确认提醒？

参考回答： 先将自然语言转换为结构化监控规则，让用户确认地址、网络、阈值与通知频率。规则执行由确定性任务完成，模型负责解释事件和生成摘要。

采用事件去重、窗口聚合、冷却期和阈值滞回，状态变化才发送提醒。区分初步观察与最终确认，重组后可发更正。Token 元数据、精度和估值来源需要校验，不能按 symbol 判断资产身份。

取舍与验证： 低延迟与误报率有取舍。回放历史或模拟事件，检查重复通知、边界抖动、源数据缺失和重组更正；不要默认一个地址等于一个真实用户。

78. 用户说“资金没到账”，客服 Agent 应怎样处理？【P0】

先澄清： 是链上转账、平台入账还是订单结算？需要哪条链、交易哈希和账户身份？只请求完成核查所需的信息。

参考回答： 先区分未提交、待确认、链上失败、链上成功但平台未记账等状态，使用授权工具查询并返回来源与更新时间。链上成功不一定等于业务账户已入账，还要核对目标地址、网络、Token 和业务规则。

涉及平台账务差异时创建可追踪工单并附核查证据；Agent 不自行退款或要求用户提供私钥。每次状态更新使用同一问题 ID，避免重复创建工单。

取舍与验证： 自动化应提高定位效率，不越过账务权限。测试错误网络、无效哈希、第三方账户查询、上游超时和重复提交。

我的经历切入： 酒店 SaaS 支付异步查询和超时订单经验可迁移，但不能说等同于链上支付实践。

79. 数据库恢复到十分钟前，队列里还有旧任务，怎么恢复服务？【P0】

先澄清： 恢复点与实际丢失范围是什么？外部操作是否仍继续发生？队列、业务库、Checkpoint、索引分别恢复到什么时间？

参考回答： 先停止有副作用的消费，建立恢复边界，对账外部操作与内部记录，再允许重放。数据库回滚后原有幂等记录可能消失，所以不能直接假设旧任务都可以安全重跑。

以原始事件或源系统补齐数据，逐项恢复业务状态、任务状态和索引。无法自动确定的动作保持待核对，先恢复只读能力，再恢复写入和执行能力。定义 RPO/RTO 时，把队列和外部依赖一起考虑。

取舍与验证： 恢复速度与一致性之间要按业务优先级选择。定期演练备份恢复、外部对账、重复消费与数据补齐；“有备份”不等于“能可靠恢复”。

80. 产品说“做一个能回答所有 Web3 问题的 Agent”，你怎么推进？【P0】

先澄清： 首批用户是谁，最频繁的三个任务是什么，哪些行为明确不做？是否有数据授权、真实问题样本和验收负责人？

参考回答： 我会把抽象需求拆成可观察的用户任务，例如市场规则问答、行情解释、钱包事件查询。先比较业务价值、数据可得性、实现成本与失败影响，选择一条只读闭环。

用真实问题定义验收标准并展示可运行原型，记录系统不能完成的请求，再决定扩展方向。需求变化通过范围与里程碑调整体现，不能用无限增加工具掩盖目标不清楚。

取舍与验证： 第一版覆盖范围有限，但每个支持的任务应能解释来源、失败和成本。和产品共同审查失败样本，确认下一轮是补数据、改交互还是增加能力。

我的经历切入： 从 0 到 1 的 SaaS 与企业平台经验，体现能推进需求澄清和交付，而不仅是等待完整需求。

回答中容易踩的坑

  • Checkpoint、MQ、Redis 锁都不等于外部业务 exactly-once。
  • thread_id、模型传入的用户 ID 和钱包地址不等于身份授权。
  • async 不等于所有内部代码非阻塞，SSE 断开不等于任务取消。
  • 高相似度不等于事实正确，多模型一致不等于证据可靠。
  • 价格不等于客观概率，交易数不等于用户数，观察到交易不等于最终确定。
  • 新框架不天然优于旧框架，优化结果必须有相同口径的测量。
