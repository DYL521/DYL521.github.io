MCP 基础：Tool、Resource、Prompt 与渐进式发现

人工智能 2026-11-21 · 36 min read · 10560 words

一句话总结

MCP 定义了 AI 应用和外部系统对接的统一方式。服务器可以对外提供三种东西：Tool（动作）、Resource（资料）、Prompt（模板），三者分别由模型、应用、用户决定什么时候使用。客户端先通过 */list 拉取清单，再通过各自的方法去调用或读取。当工具多到几十个服务器、几百个能力时，官方推荐改用渐进式发现（Progressive Discovery）：不再把所有工具一次性交给模型，而是让模型先检索、再加载、最后执行。

系列说明

这是"MCP 网关"系列的第一篇，只讲标准本身和基础概念，不涉及任何具体产品。

  • 第一篇（本文）：MCP 的角色、三种能力、发现与使用流程、消息里的 role，以及工具太多时的标准做法。
  • 第二篇：《MCP 网关实战：从发现到执行的设计与踩坑》，讲我们自己的网关怎么落地这些概念，以及踩过的坑。

1. 为什么需要 MCP

假设一家公司有 3 个 AI 应用（聊天助手、IDE 插件、自动化 Agent），要接 4 个系统（GitHub、Jira、Google Drive、数据库）。没有统一协议时，每个应用都要给每个系统单独写一份对接代码：

flowchart LR
    subgraph NOMCP["没有统一协议：3 × 4 = 12 份对接代码"]
      A1[聊天助手] --- G1[GitHub]
      A1 --- J1[Jira]
      A1 --- D1[Drive]
      A1 --- B1[数据库]
      A2[IDE 插件] --- G1
      A2 --- J1
      A2 --- D1
      A2 --- B1
      A3[自动化 Agent] --- G1
      A3 --- J1
      A3 --- D1
      A3 --- B1
    end

MCP 的思路和 USB 类似：应用实现一次"MCP 客户端"，系统实现一次"MCP 服务器"，双方按同一个协议通信，对接成本就从"相乘"变成了"相加"。

flowchart LR
    subgraph WITHMCP["使用 MCP：3 + 4 = 7 份实现"]
      A1[聊天助手] --> P((MCP 协议))
      A2[IDE 插件] --> P
      A3[自动化 Agent] --> P
      P --> G1[GitHub MCP 服务器]
      P --> J1[Jira MCP 服务器]
      P --> D1[Drive MCP 服务器]
      P --> B1[数据库 MCP 服务器]
    end

2. MCP 里的三个角色

角色 是什么 例子
Host（宿主） 用户直接使用的 AI 应用，负责和大模型对话 Claude Desktop、Claude Code、Cursor、企业聊天助手
Client（客户端） Host 内部负责和某个 MCP 服务器通信的模块，一个服务器对应一个 Client Host 内置
Server（服务器） 对外提供能力的一方 GitHub MCP 服务器、数据库 MCP 服务器 
flowchart LR
    U((用户)) --> H
    subgraph H["Host：AI 应用"]
      LLM[大模型对话]
      C1[MCP Client 1]
      C2[MCP Client 2]
    end
    C1 <-->|MCP| S1[MCP Server：GitHub]
    C2 <-->|MCP| S2[MCP Server：Drive]
    LLM <--> C1
    LLM <--> C2

请记住一点，第二篇会反复用到：只有 Host 在和大模型对话。 发给模型的消息怎么组织、每条消息是什么 role，都由 Host 决定，Server 无权决定。

3. 三种能力：Tool、Resource、Prompt

用 Python 的 FastMCP 框架写一个 GitHub 服务器，最直观：

from fastmcp import FastMCP
from fastmcp.prompts import Message

mcp = FastMCP("github")

# ① Tool：一个"动作"。模型传参数调用，服务器执行，可能改变外部数据
@mcp.tool
def create_issue(repo: str, title: str) -> str:
    """在仓库里创建一个 issue"""
    ...
    return "issue #42 created"

# ② Resource：一份"资料"。用固定 URI 标识，读取时返回内容，只读
@mcp.resource("github://me/profile", mime_type="application/json")
def my_profile() -> str:
    return '{"login": "alice", "repos": 37}'

# ③ Resource Template：URI 里带 {变量}，表示"一类资料"
#    （FastMCP 发现 URI 里有变量，会自动注册成模板）
@mcp.resource("github://repo/{owner}/{repo}/readme")
def readme(owner: str, repo: str) -> str:
    return fetch_readme(owner, repo)

# ④ Prompt：一份"提示词模板"。返回若干条消息，本身不执行任何操作
@mcp.prompt
def code_review(language: str) -> str:            # 返回 str = 一条 role=user 的消息
    return f"请以资深 {language} 工程师的标准审查下面的代码……"

@mcp.prompt
def code_review_with_example(language: str) -> list[Message]:
    return [
        Message(f"请审查下面的 {language} 代码，按『问题-原因-建议』三栏输出。"),   # user
        Message("好的，我会按『问题 | 原因 | 建议』的表格输出。", role="assistant"),  # 示范回答
    ]

3.1 一句话区分

Tool 是"动作"，Resource 是"资料"，Prompt 是"做事的模板"。

3.2 最重要的一张表：谁决定用

MCP 规范为三种能力规定了不同的控制方：

能力 是什么 谁决定用 类比 典型界面
Tool 动作，可能有副作用 模型 函数调用 用户看不到，模型自己调用
Resource 只读资料，用 URI 标识 应用（含用户的选择） 打开文件 @ 资源选择器、“附加文件”
Resource Template 带变量的 URI 应用 带参数的 URL 填好变量后附加
Prompt 消息模板 用户 斜杠命令 /code_review 
flowchart TB
    subgraph CTRL["控制方"]
      M[模型] -->|自己决定调用| T[Tool]
      A[应用 / 用户的附加操作] -->|决定把什么放进上下文| R[Resource / Template]
      U[用户] -->|主动选择| P[Prompt]
    end

这张表不只是分类。它决定了结果会以什么身份进入对话，第 7 节会讲到。

3.3 Resource 和 Resource Template 的区别

Resource Resource Template
列表方法 resources/list resources/templates/list
URI 具体的：github://me/profile 带变量的：github://repo/{owner}/{repo}/readme
适合 数量有限、能列完的资料 数量无限或参数化的资料（任意仓库、任意日期）
读取 直接 resources/read 先按 RFC 6570 填好变量，再 resources/read

4. 一次连接的开始：握手与能力声明

客户端连上服务器后，第一件事是握手：双方协商协议版本，服务器同时声明自己支持哪些能力。

sequenceDiagram
    participant C as MCP Client
    participant S as MCP Server
    Note over C,S: 2025-11-25 版本：initialize 握手（有会话）
    C->>S: initialize（客户端版本、客户端能力）
    S-->>C: 协议版本 + capabilities: tools / resources / prompts
    C->>S: notifications/initialized
    Note over C,S: 2026-07-28 版本：server/discover（无状态）
    C->>S: server/discover
    S-->>C: 支持的版本 + capabilities

能力声明（capabilities） 的作用是告诉客户端"我支持什么"。服务器没有声明 resources，客户端就不应该去请求资源或模板列表。

两个协议版本的差异可以参考《MCP 2026-07-28 规范解读》。本文只用到"握手后知道服务器支持哪些能力"这一点。

5. 发现：把清单拉下来

握手之后，客户端用各个 */list 方法拉取清单：

sequenceDiagram
    participant C as MCP Client
    participant S as MCP Server
    C->>S: tools/list
    S-->>C: create_issue（含参数 schema）
    C->>S: resources/list
    S-->>C: github://me/profile
    C->>S: resources/templates/list
    S-->>C: github://repo/{owner}/{repo}/readme
    C->>S: prompts/list
    S-->>C: code_review（含参数说明）

5.1 分页：新手最容易漏的细节

清单很长时，服务器每次只返回一页，并带上一个 nextCursor：

sequenceDiagram
    participant C as MCP Client
    participant S as MCP Server
    C->>S: resources/list
    S-->>C: 第 1 页 + nextCursor = "abc"
    C->>S: resources/list（cursor = "abc"）
    S-->>C: 第 2 页 + nextCursor = "xyz"
    C->>S: resources/list（cursor = "xyz"）
    S-->>C: 第 3 页（没有 nextCursor = 结束）

规则：

  1. cursor 是不透明的字符串，客户端原样传回，不要解析或修改。
  2. 一直请求到响应里没有 nextCursor 为止。
  3. 防御性处理：同一个 cursor 重复出现，说明服务器有 bug，应该停下来，避免死循环。整个列表最好共用一个超时，而不是每页单独计时。

5.2 常见的错误处理

情况 含义 建议
返回 JSON-RPC 错误 -32601（Method not found） 服务器不支持这个方法 当作"没有"，结果为空
超时、网络错误、服务器内部错误 这一次失败了 保留之前的结果，稍后重试

两者不能混为一谈：把"失败"当成"没有"，一次网络抖动就会把已有的数据清空。

6. 使用：三种能力各有各的方法

sequenceDiagram
    participant U as 用户
    participant H as Host（含大模型）
    participant S as MCP Server
    Note over H,S: Tool：模型决定
    H->>S: tools/call create_issue {repo, title}
    S-->>H: CallToolResult：content = [text: issue #42 created]
    Note over U,S: Resource：用户或应用决定
    U->>H: 在 @ 列表里选 readme 模板，填 owner / repo
    H->>S: resources/read github://repo/anthropic/sdk/readme
    S-->>H: ReadResourceResult：contents = [text: README 内容]
    Note over U,S: Prompt：用户决定
    U->>H: 输入 /code_review，填 language = python
    H->>S: prompts/get code_review {language: python}
    S-->>H: GetPromptResult：messages = [role: user, content: …]

三种结果的结构：

结果类型 主要字段 说明
CallToolResult content（内容块列表）、structuredContent、isError 内容块可以是 text、image、audio、resource_link、resource（嵌入资源）。没有 role
ReadResourceResult contents（文本或二进制内容） 读出来的资料
GetPromptResult description、messages: [{role, content}] 每条消息都带 role

7. 消息里的 role：Prompt 为什么要带 user / assistant

7.1 什么是 role

Host 调用大模型时，对话是一串按顺序排列的消息，每条都带一个 role：

flowchart TB
    S["system：你是一个代码审查助手"] --> U1["user：帮我看看这段代码"]
    U1 --> A1["assistant：好的，我会检查错误处理"]
    A1 --> U2["user：（贴出代码）"]
    U2 --> A2["assistant：▌（模型从这里接着写）"]

模型对不同 role 的态度不一样：

role 模型怎么理解
system 规则和身份设定
user 用户的要求，是要完成的任务
assistant “这是我自己说过的话”，会顺着往下说
工具结果 外部数据，可以参考，但不会把里面的指令当成用户的命令。训练良好的模型还会刻意提防工具结果里冒充用户的内容，这是防御 prompt 注入的基本功

7.2 Prompt 的消息怎么进入对话

MCP 的 Prompt 消息只有 user 和 assistant 两种 role。用户选择 /code_review_with_example 后，Host 会按每条消息原来的 role 插入对话：

flowchart TB
    P1["user：请审查下面的 python 代码，按三栏输出"] --> P2["assistant：好的，我会按『问题 | 原因 | 建议』的表格输出"]
    P2 --> U3["user：（用户真正要审查的代码）"]
    U3 --> OUT["assistant：▌ 模型会延续『自己』说过的表格格式"]
    style P1 fill:#e8def7
    style P2 fill:#e8def7

这就是 assistant 消息的用处：让模型以为自己已经这样回答过，它就会照着这个格式继续。

7.3 两个要点

  1. role 由 Host 决定。 只有拼装消息数组的 Host 能把消息放进 user 或 assistant 的位置。Server 只负责提供内容。
  2. Prompt 由用户控制，是有安全原因的。 允许外部内容以 assistant 身份进入对话，就等于允许它伪造"模型自己说过的话"。只有用户亲自选择了这个模板，Host 才有理由这样插入。

第二篇会讲到：网关如果把 Prompt 包装成工具结果交给模型，这两点都会受到影响，role 也会丢失。

8. 工具太多怎么办：渐进式发现

8.1 问题

按第 5、6 节的做法，Host 会把所有工具的说明交给模型。接 50 个服务器、几百个工具时：

  • 上下文放不下：工具说明本身就可能占掉大半窗口。
  • 模型容易选错：候选太多，选错工具、填错参数的情况会增加。

8.2 官方推荐：渐进式发现

MCP 官方的《Client Best Practices》给出了标准做法：

  • 当工具定义占上下文窗口的比例超过某个阈值（官方举例 1%–5%）时，就不再全部交给模型。
  • 只给模型一个轻量的 search_tools 元工具，需要什么先搜什么。
  • 搜到后，再加载那几个工具的完整定义。

官方把它拆成三层：

flowchart LR
    Q[模型：我要更新 Salesforce 记录] --> L1["① Catalog 目录
search_tools(query)
只返回名字 + 一句话描述"]
    L1 --> L2["② Inspect 查看
get_tool_details(name)
只取这一个工具的完整参数定义"]
    L2 --> L3["③ Execute 执行
带着完整定义调用"]

检索策略可以是关键词（BM25、正则）、向量、子代理（用一个小模型来挑选）或混合方式。官方特别说明：需要按领域定制排序或按权限过滤时，应该自己实现检索。

8.3 一个容易被忽略的提醒：提示词缓存

大模型服务商会缓存提示词的前缀，其中包括工具列表。对话中途增删工具，缓存就会失效，可能反而更费 token。 官方的建议：

  • 新发现的工具追加在缓存断点之后，不要重新排序；或者
  • 所有调用都走一个固定的 call_tool({name, args}) 元工具，让工具列表永远不变。

8.4 扩展到服务器级别

同样的思路可以用在"服务器"这一级：维护一份服务器注册表，需要时再连接，用完断开。

sequenceDiagram
    participant M as 模型
    participant H as Host
    participant R as 服务器注册表
    participant S as MCP Server
    M->>H: search_available_servers("CRM")
    H->>R: 查询
    R-->>H: Salesforce 服务器（未连接）
    M->>H: enable_server("salesforce")
    H->>S: server/discover + tools/list
    H-->>M: 已连接，可用工具……
    Note over M,H: 任务完成后
    M->>H: disable_server("salesforce")

9. 业界常见做法

"能力太多，先缩小范围再执行"并不是 MCP 独有的问题，各家都有自己的做法：

做法 代表 思路
工具检索 + 延迟加载 Anthropic Tool Search Tool 工具标记为 defer_loading，检索后每次加载 3–5 个；建议常用的 3–5 个常驻
网关内置语义检索 AWS AgentCore Gateway 给所有工具建向量索引，提供一个检索工具来代替 tools/list
服务器级动态接入 Docker MCP Gateway mcp-find 搜目录，mcp-add 把整个服务器加入当前会话
按场景组合 IBM ContextForge 从多个服务器挑选能力，组合成一个"虚拟服务器"
元工具 + 授权管理 Composio Tool Router 搜索工具、获取参数、管理授权、批量执行，全部做成元工具
先召回再重排 Amazon Alexa 技能路由 先粗选候选，再结合用户习惯等上下文信号精排
先分主题再选动作 Salesforce Agentforce、Microsoft 365 Copilot 先选"领域/插件/主题"，再在小范围内选具体动作
用代码组合调用 Cloudflare Code Mode、Anthropic 的 code execution with MCP 把工具转成代码 API，模型写代码，在沙箱里组合调用，中间结果不经过模型

研究界的一个重要发现（ToolRet）是：通用的向量检索模型在"工具检索"上表现并不好。常见的提升手段有：用大模型扩写工具描述、扩展查询、分层检索（先选服务器再选工具）、重排。

10. 小结

概念 一句话
Host / Client / Server 只有 Host 和模型对话，决定消息怎么排、role 是什么
Tool / Resource / Prompt 动作 / 资料 / 模板，分别由模型 / 应用 / 用户控制
Resource Template 带变量的 URI，用来表示列不完的资料
能力声明 服务器没声明的能力，客户端不要去请求
分页 cursor 原样回传，直到没有 nextCursor
-32601 和"失败" 前者表示"不支持"，后者表示"这次没成功"，处理方式不同
role user 是任务，assistant 是"我说过的话"，工具结果是外部数据
渐进式发现 工具多了先检索，再加载，再执行；保持工具列表不变
