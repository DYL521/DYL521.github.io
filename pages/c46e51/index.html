01.第三方登录解决什么问题

第三方登录允许用户使用 QQ、微信、微博等已有账号登录本站，减少重复注册和记忆密码的成本。常见实现基于 OAuth 2.0 授权码流程；如果平台支持 OpenID Connect（OIDC），还可以通过 ID Token 获得标准化的身份信息。

需要区分两个概念：

  • OAuth 2.0主要解决授权，即“允许本站访问哪些资源”。
  • OIDC在 OAuth 2.0 之上补充身份层，回答“当前用户是谁”。
  • JWT只是一种令牌格式，可以与 OAuth 2.0/OIDC 配合，但第三方登录并不等于 JWT 登录。

下图是早期以微博为例的对接示意，核心过程是“跳转第三方授权 → 获得 code → 后端换取访问令牌 → 查询用户 → 绑定本站账号”。生产实现建议让第三方回调直接进入本站后端，并补上 state、PKCE 等安全校验。

02.参与角色

角色 示例 职责
资源所有者 正在登录的用户 决定是否授权
客户端 本站 Web 应用 发起授权并维护自己的登录态
授权服务器 微信、微博等开放平台 验证用户、发放 code 和访问令牌
资源服务器 第三方用户信息接口 根据访问令牌提供用户资料

对接前通常要在开放平台创建应用，配置固定回调地址，并取得 client_id 和 client_secret。client_secret 只能保存在服务端；SPA、移动端等公开客户端不能安全保存它，应使用平台支持的 PKCE 流程。

03.推荐的授权码登录流程

3.1 发起授权

用户点击“使用微博登录”后，本站后端生成随机且一次性的 state，把它与本站登录会话关联并设置较短有效期，然后跳转到第三方授权页：

https://provider.example/oauth/authorize
  ?client_id=CLIENT_ID
  &redirect_uri=https%3A%2F%2Fexample.com%2Foauth%2Fcallback%2Fweibo
  &response_type=code
  &scope=basic
  &state=RANDOM_STATE
  • redirect_uri 必须与平台登记值精确匹配。
  • state 用于防止登录 CSRF，不能使用固定字符串或仅依赖前端传入值。
  • 平台支持 OIDC 时加入随机 nonce；支持 PKCE 时生成 code_verifier 和 code_challenge，并保存 verifier 供后续换令牌使用。

3.2 用户授权并回调本站

用户在第三方页面确认授权后，第三方跳转到本站回调地址，并携带一次性 code 和之前的 state。推荐直接回调本站后端：

GET /oauth/callback/weibo?code=AUTH_CODE&state=RANDOM_STATE

后端必须验证 state 是否存在、属于当前登录会话且未被使用，验证后立即作废。校验失败就终止登录，不能继续用 code 查询用户。

3.3 服务端换取令牌并获取身份

后端通过 HTTPS 请求第三方令牌接口，提交 client_id、授权码、回调地址以及服务端密钥或 PKCE verifier。第三方返回 access_token 后，后端再调用用户资料接口；OIDC 场景还要验证 ID Token 的签名、iss、aud、exp 和 nonce。

**不能信任浏览器直接提交的 openid、昵称或头像。**可信身份必须来自服务端换取令牌后的接口响应，或经过完整验签和声明校验的 ID Token，否则攻击者可以伪造参数登录他人账号。

第三方访问令牌也不应直接当成本站会话发给所有前端。它只用于访问第三方资源；若确需保存，应加密存储、限制权限并按照过期时间管理，避免写入日志。

04.绑定本站账号

拿到可信身份后，使用平台名和平台用户标识查询绑定关系：

(provider = "weibo", openid = "...")
  • openid 通常只在同一个第三方应用内唯一。
  • 某些开放平台提供 unionid，可用于同一开放平台主体下多个应用之间识别同一用户；是否提供及其语义以平台文档为准。
  • 数据库应对 (provider, openid) 建唯一约束，防止并发登录创建重复绑定。

处理分支如下：

  1. 已有绑定：确认本站用户未被禁用，然后签发本站自己的 Session 或访问令牌。
  2. 没有绑定，选择注册：创建本站用户与第三方身份的唯一绑定，再建立登录态。
  3. 没有绑定，选择关联已有账号：要求用户重新完成本站登录或其他强验证，通过后再绑定，不能只凭前端提交的用户名、密码或 openid 完成操作。
  4. 第三方资料与本站资料冲突：不要仅凭相同邮箱或手机号自动合并，除非该字段已经由第三方可靠验证且业务明确允许。

注册与绑定应放在同一个事务中，捕获唯一约束冲突后重新查询，避免用户重复点击或并发回调产生多个账号。

05.登录成功之后

第三方只负责证明外部身份，本站仍需建立自己的权限体系：

  • 创建本站 Session 或短期访问令牌，设置合理的过期时间。
  • 根据 state 关联的原始地址做一次受控跳转，不允许任意 return_url 造成开放重定向。
  • 授权码和 state 都不复用，回调地址不要写入敏感日志。
  • 用户解绑时至少保留一种可用登录方式，避免账号彻底失去访问入口。
  • 本站退出只代表本站会话结束，不应擅自退出用户的第三方账号。

06.安全检查清单

  1. 全程 HTTPS，client_secret 和第三方访问令牌不暴露给不可信前端。
  2. 校验并一次性消费 state，OIDC 同时校验 nonce，公开客户端使用 PKCE（平台支持时）。
  3. 回调地址精确匹配，授权码短期有效且只能使用一次。
  4. 用户身份由后端获取或验证，不信任前端提交的第三方用户 ID。
  5. 对登录、注册、绑定和换令牌接口限流，记录不含令牌的安全审计日志。
  6. 明确账号绑定、解绑、注销和第三方撤销授权后的处理策略。

一句话总结：第三方平台证明“你是谁”，本站决定“你能做什么”；code 换身份必须在可信后端完成，本站最终使用自己的登录态和权限体系。
