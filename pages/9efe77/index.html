Redis哨兵模式

01.redis哨兵模式

  • redis哨兵模式请占时参考我的博客园
  • redis哨兵模式

1.1 为什么需要哨兵

普通的主从复制（见《部署Redis主从》）解决了数据备份和读扩展，但有一个致命问题：主节点挂了之后不会自动切换，需要人工把某个从节点 REPLICAOF NO ONE 提升为主，再修改其他从节点和所有客户端的配置，期间写服务不可用。

Redis Sentinel（哨兵）就是官方提供的高可用方案，它负责：

  • 监控（Monitoring）：持续检查主、从节点是否正常；
  • 通知（Notification）：节点出问题时通过 API / 发布订阅通知管理员或其他程序；
  • 自动故障转移（Automatic failover）：主节点故障时，自动选一个从节点提升为新主，并让其他从节点复制新主；
  • 配置提供者（Configuration provider）：客户端不直接写死主节点地址，而是向哨兵询问"当前主节点是谁"。

  • 数据节点：一个 master + 若干 replica，就是普通的 redis-server；
  • 哨兵节点：特殊模式运行的 Redis 进程，不存储业务数据，默认端口 26379；
  • 哨兵之间互相发现：通过主节点的 __sentinel__:hello 频道发布自己的信息，所以配置里只需要写主节点地址，从节点和其他哨兵都能自动发现。

哨兵内部有三个定时任务：

周期 动作 作用
每 10 秒 向主、从节点发送 INFO 发现从节点、获取复制信息
每 2 秒 向主节点的 __sentinel__:hello 频道发布消息 哨兵之间互相发现、交换主节点视图
每 1 秒 向主、从、其他哨兵发送 PING 心跳检测，判断节点是否下线

以上周期以 Redis 官方文档描述为准，不同版本可能略有差异。

02.主观下线与客观下线

2.1 SDOWN（主观下线）

某个哨兵在 down-after-milliseconds 时间内没有收到节点的有效 PING 回复，就认为该节点主观下线。这只是"我自己觉得它挂了"，可能是这个哨兵自己的网络问题。

对从节点和其他哨兵，判断到主观下线就结束了；只有主节点才会进入下一步。

2.2 ODOWN（客观下线）

哨兵认为主节点主观下线后，会询问其他哨兵（SENTINEL is-master-down-by-addr）。当认为主节点下线的哨兵数量达到 quorum 时，主节点被标记为客观下线，开始故障转移流程。

2.3 quorum 与多数派

这是最容易混淆的面试点：

  • quorum：判定客观下线需要的哨兵票数，由 sentinel monitor 最后一个参数配置；
  • 多数派（majority）：真正执行故障转移，需要选出领头哨兵，这一步需要超过半数哨兵投票同意。

例如 5 个哨兵、quorum = 2：2 个哨兵认为主挂了就能判定 ODOWN，但要执行故障转移仍需要至少 3 个哨兵在线并投票。所以：

  • quorum 设小，故障检测更敏感，但误判可能性更高；
  • 哨兵数量建议奇数且至少 3 个，部署在不同物理机/可用区；
  • 2 个哨兵是不安全的：任一哨兵挂掉，剩下 1 个达不到多数派，无法故障转移。

03.领头哨兵选举与故障转移

3.1 选举领头哨兵

判定 ODOWN 后，多个哨兵可能同时想执行故障转移，需要先选出一个 leader，算法类似 Raft：

  1. 发现 ODOWN 的哨兵把自己的配置纪元（epoch）加 1，向其他哨兵请求投票；
  2. 每个哨兵在一个纪元内只投一票，先到先得；
  3. 获得超过半数且不少于 quorum 的票数即成为 leader；
  4. 如果本轮没选出来，等待一段时间后进入下一个纪元重新选举。

3.2 选择新的主节点

leader 从从节点中筛选：

  1. 排除不健康的：已下线、最近没有回复 PING、与原主节点断开时间过长的从节点；
  2. 按 replica-priority（旧版本叫 slave-priority）排序，值越小优先级越高，为 0 表示永不提升为主；
  3. 优先级相同，选择复制偏移量（offset）最大的，即数据最新的；
  4. 仍然相同，选择 run ID 最小的。

3.3 执行切换

  1. 对选中的从节点执行 REPLICAOF NO ONE，使其成为新主；
  2. 让其他从节点执行 REPLICAOF <新主 IP> <端口>，复制新主（并发数受 parallel-syncs 控制）；
  3. 更新哨兵自身配置，并通过 +switch-master 消息通知客户端；
  4. 原主节点恢复上线后，哨兵会把它降级为新主的从节点。

04.部署配置示例

假设环境（沿用主从部署那篇的机器规划）：

角色 IP 端口
master 192.168.56.65 6379
replica 192.168.56.66 6379
replica 192.168.56.67 6379
sentinel × 3 三台机器各一个 26379

4.1 sentinel.conf

port 26379
daemonize yes
logfile "/var/log/redis/sentinel.log"
dir "/tmp"

# 监控名为 mymaster 的主节点，quorum = 2
sentinel monitor mymaster 192.168.56.65 6379 2

# 主节点设置了密码时需要配置
sentinel auth-pass mymaster yourpassword

# 30 秒无有效回复判为主观下线
sentinel down-after-milliseconds mymaster 30000

# 故障转移后，同时向新主发起同步的从节点数量，越小对服务影响越小
sentinel parallel-syncs mymaster 1

# 故障转移超时时间
sentinel failover-timeout mymaster 180000

注意：哨兵运行时会改写自己的配置文件（记录发现的从节点、其他哨兵、当前纪元），所以配置文件必须可写，也不要多个哨兵共用同一份文件。

4.2 启动与检查

# 两种启动方式等价
redis-sentinel /usr/local/redis/sentinel.conf
redis-server /usr/local/redis/sentinel.conf --sentinel

# 连接哨兵查看状态
redis-cli -p 26379
127.0.0.1:26379> SENTINEL get-master-addr-by-name mymaster
1) "192.168.56.65"
2) "6379"
127.0.0.1:26379> SENTINEL masters
127.0.0.1:26379> SENTINEL replicas mymaster      # 旧版本用 SENTINEL slaves
127.0.0.1:26379> SENTINEL sentinels mymaster
127.0.0.1:26379> SENTINEL ckquorum mymaster      # 检查当前哨兵数能否满足 quorum 和多数派

4.3 模拟故障转移

# 方式一：直接停掉主节点，等待 down-after-milliseconds 之后观察日志
redis-cli -h 192.168.56.65 -p 6379 shutdown

# 方式二：手动触发故障转移（不需要其他哨兵同意）
redis-cli -p 26379 SENTINEL failover mymaster

# 再次查询主节点地址，应该已经变成某个从节点
redis-cli -p 26379 SENTINEL get-master-addr-by-name mymaster

哨兵日志中可以看到 +sdown、+odown、+try-failover、+elected-leader、+switch-master 等事件。

05.客户端如何发现主节点

客户端连接的是哨兵地址列表，由客户端库负责询问主节点地址，并在切换后自动重连。

Python（redis-py）：

from redis.sentinel import Sentinel

sentinel = Sentinel(
    [("192.168.56.65", 26379), ("192.168.56.66", 26379), ("192.168.56.67", 26379)],
    socket_timeout=0.5,
)

master = sentinel.master_for("mymaster", password="yourpassword", socket_timeout=0.5)
replica = sentinel.slave_for("mymaster", password="yourpassword", socket_timeout=0.5)

master.set("foo", "bar")   # 写主
print(replica.get("foo"))  # 读从（可能读到旧数据）

Go（go-redis）：

rdb := redis.NewFailoverClient(&redis.FailoverOptions{
	MasterName:    "mymaster",
	SentinelAddrs: []string{"192.168.56.65:26379", "192.168.56.66:26379", "192.168.56.67:26379"},
	Password:      "yourpassword",
})
err := rdb.Set(ctx, "foo", "bar", 0).Err()

06.脑裂与数据丢失

6.1 脑裂是怎么产生的

原主节点和客户端在一个网络分区，哨兵和从节点在另一个分区：

  1. 哨兵认为主节点下线，把某个从节点提升为新主；
  2. 旧主其实还活着，客户端继续往旧主写数据；
  3. 网络恢复后，旧主被降级为从节点，清空自己的数据去同步新主，分区期间写入旧主的数据全部丢失。

此外，主从复制是异步的，主节点宕机时还没同步到从节点的数据，在故障转移后也会丢失。

6.2 缓解办法

在数据节点（redis.conf）中配置：

# 至少有 1 个从节点在线，且复制延迟不超过 10 秒，主节点才接受写入
min-replicas-to-write 1
min-replicas-max-lag 10

旧版本中对应的配置名是 min-slaves-to-write / min-slaves-max-lag。

效果：旧主被隔离后，连不上从节点，超过 10 秒就拒绝写入，从而把丢失的数据控制在一个时间窗口内。代价是从节点全部故障时主节点也不可写，可用性换一致性。

需要明确：Redis Sentinel 无法做到"零数据丢失"，对强一致有要求的数据（如资金）不要只依赖 Redis。

07.哨兵 vs Cluster

对比项 哨兵模式 Redis Cluster
解决的问题 主从高可用、自动故障转移 高可用 + 数据分片、水平扩展
写能力 只有一个主节点，写能力受单机限制 多个主节点分摊 16384 个哈希槽
容量 受单机内存限制 可以通过加节点扩容
额外组件 需要单独部署哨兵进程 节点内置故障检测，不需要哨兵
客户端 需要支持哨兵的客户端 需要支持集群（MOVED/ASK 重定向）的客户端
多 key 操作 无限制 跨槽的多 key 命令、事务、Lua 受限（可用 hash tag）
适用场景 数据量单机放得下，主要需要高可用 数据量或写 QPS 超出单机能力

08.面试题速答

  • 哨兵的作用？ 监控、通知、自动故障转移、配置提供。
  • 主观下线和客观下线的区别？ 单个哨兵判断为 SDOWN；达到 quorum 个哨兵同意为 ODOWN，只针对主节点。
  • quorum 和多数派的关系？ quorum 决定能否判定客观下线；执行故障转移需要多数哨兵选出 leader。
  • 新主怎么选？ 排除不健康节点 → 优先级 → 复制偏移量 → run ID。
  • 为什么至少 3 个哨兵？ 保证挂掉 1 个后仍有多数派可以完成选举。
  • 哨兵模式会丢数据吗？ 会，异步复制和脑裂都可能丢，min-replicas-to-write 只能缩小丢失窗口。
  • 哨兵和 Cluster 怎么选？ 单机能装下用哨兵，需要分片扩容用 Cluster。

小结

  • 哨兵是在主从复制基础上提供自动故障转移的高可用方案；
  • 流程：SDOWN → 达到 quorum 判 ODOWN → 多数派选出 leader → 选新主 → 切换 → 通知客户端；
  • 至少 3 个哨兵、分散部署；客户端通过哨兵获取主节点地址；
  • 用 min-replicas-to-write / min-replicas-max-lag 缓解脑裂丢数据；
  • 需要水平扩展时选择 Redis Cluster。
