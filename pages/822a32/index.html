01.mongodb评论

https://www.cnblogs.com/xiaonq/category/1395492.html

项目中评论模块（文章/商品/视频评论）用 MongoDB 存储，本文整理设计思路和面试常问点。

02.为什么评论用 MongoDB

面试官常问："评论为什么不用 MySQL？"可以从以下几点回答：

  • 数据量大、写入频繁：评论是典型的 UGC 数据，增长快，MongoDB 水平扩展（分片）比 MySQL 分库分表省事；
  • 结构灵活：评论可能带图片、@用户、表情、审核状态等字段，不同版本字段不一致，文档模型不需要频繁 ALTER TABLE；
  • 一致性要求不高：评论不涉及资金，不需要复杂的多表事务；
  • 查询模式简单：基本都是"按目标对象分页查评论"“查某条评论的回复”，不需要复杂 JOIN。

但也要说清楚边界：用户、订单等核心数据仍然放 MySQL，MongoDB 只存评论这类"量大、价值密度低"的数据。

03.Schema 设计：内嵌 vs 引用

3.1 方案一：评论全部内嵌在文章文档里（不推荐）

{
  _id: ObjectId("..."),
  title: "文章标题",
  comments: [
    { user_id: 1, content: "写得好", replies: [ { user_id: 2, content: "+1" } ] }
  ]
}

问题：

  • MongoDB 单个文档最大 16MB，热门文章评论会把文档撑爆；
  • 数组越来越大，更新时整个文档都要重写，写放大严重；
  • 无法对评论独立分页、排序，也难以按用户查"我的评论"。

内嵌适合"一对少量且随父文档一起读取"的数据，评论显然不是。

3.2 方案二：评论独立集合 + 引用（推荐）

// comments 集合
{
  _id: ObjectId("65f..."),
  target_type: "article",        // 被评论对象类型：article / goods / video
  target_id: 10086,              // 被评论对象 ID
  root_id: null,                 // 一级评论为 null；回复则指向所属一级评论
  parent_id: null,               // 直接回复的那条评论
  user: { id: 1, nickname: "张三", avatar: "https://..." },   // 冗余展示字段
  reply_to: { id: 2, nickname: "李四" },                       // 回复给谁
  content: "这篇文章写得很清楚",
  images: [],
  like_count: 0,
  reply_count: 0,
  status: 1,                     // 0 待审核 1 正常 2 删除
  created_at: ISODate("2021-02-12T14:56:21Z")
}

设计要点：

  • 冗余用户昵称、头像：读评论时不需要再查用户服务（反范式）。代价是用户改名后旧评论显示旧昵称，可以接受，或者异步批量更新；
  • root_id + parent_id 两级结构：前端常见展示是"一级评论 + 折叠的楼中楼回复"，用 root_id 一次查出某楼下所有回复；
  • 少量热门回复可以内嵌：一级评论里内嵌前 3 条回复（top_replies 数组，限制长度），列表页一次查询就能展示，这是内嵌与引用的折中。
// 回复时同时维护一级评论上的 top_replies（保留最新 3 条）和回复数
db.comments.updateOne(
  { _id: rootId },
  {
    $push: { top_replies: { $each: [replyDoc], $slice: -3 } },
    $inc: { reply_count: 1 }
  }
)

04.嵌套回复的几种模型

模型 做法 适用
两级扁平（root_id） 所有回复挂在一级评论下，用 reply_to 表示回复对象 绝大多数 App（抖音、B 站类）
父引用（parent_id） 每条记录只存父 ID，递归查询 层级不深的树
物化路径（path） 存 path: "a1/b2/c3"，用前缀正则查子树 需要无限层级的论坛

实际项目推荐两级扁平：查询简单、索引好建，前端也没法展示太深的层级。

05.分页

5.1 skip + limit 的问题

db.comments.find({ target_type: "article", target_id: 10086, root_id: null })
  .sort({ created_at: -1 }).skip(10000).limit(20)

skip 需要先扫描并丢弃前面的文档，页数越深越慢。

5.2 游标分页（推荐）

用上一页最后一条记录作为游标，按 (created_at, _id) 继续往后查：

db.comments.find({
  target_type: "article", target_id: 10086, root_id: null, status: 1,
  $or: [
    { created_at: { $lt: lastCreatedAt } },
    { created_at: lastCreatedAt, _id: { $lt: lastId } }
  ]
}).sort({ created_at: -1, _id: -1 }).limit(20)
  • 加 _id 是为了处理同一时间的多条评论，防止漏数据或重复；
  • ObjectId 本身前 4 字节是时间戳，只按时间排序时也可以直接用 _id < lastId 做游标；
  • 评论列表本身就是"上拉加载更多"，不需要跳页，天然适合游标分页。

按热度排序（点赞数）时，游标改为 (like_count, _id)，但点赞数会变化，翻页时可能出现轻微重复，通常前端按 _id 去重即可。

06.索引设计

// 一级评论列表：按对象查、按时间倒序
db.comments.createIndex({ target_type: 1, target_id: 1, root_id: 1, created_at: -1, _id: -1 })

// 某楼的回复列表
db.comments.createIndex({ root_id: 1, created_at: 1 })

// 我的评论
db.comments.createIndex({ "user.id": 1, created_at: -1 })
  • 遵循 ESR 原则：等值条件（Equality）在前，排序（Sort）其次，范围（Range）在后；
  • 用 explain("executionStats") 确认走的是 IXSCAN 而不是 COLLSCAN，且没有内存排序（SORT 阶段）；
  • status 选择性低，不一定要放进索引，可以过滤时顺带处理。

07.计数

评论数、点赞数有两种做法：

  1. 文档内 $inc：MongoDB 单文档更新是原子的，$inc 不会出现并发覆盖问题；
  2. Redis 计数 + 异步落库：热门内容写入频繁时，先在 Redis INCR，定时批量写回 MongoDB，减少热点文档的写竞争。

点赞要防重复：单独建 comment_likes 集合，{comment_id, user_id} 上建唯一索引，插入成功再 $inc，重复点赞会触发唯一键冲突直接忽略。

from pymongo import MongoClient
from pymongo.errors import DuplicateKeyError

db = MongoClient("mongodb://localhost:27017")["blog"]

def like_comment(comment_id, user_id):
    try:
        db.comment_likes.insert_one({"comment_id": comment_id, "user_id": user_id})
    except DuplicateKeyError:
        return False  # 已经点过赞
    db.comments.update_one({"_id": comment_id}, {"$inc": {"like_count": 1}})
    return True

两步操作之间不是事务，极端情况下计数可能和明细不一致，可以定期按明细对账；对一致性要求高也可以使用 MongoDB 4.0+ 的副本集多文档事务，但会牺牲性能。

08.分片键选择

数据量大到单个副本集扛不住时需要分片，片键选择是面试重点：

候选片键 评价
_id（ObjectId） 单调递增，所有新写入都落在最后一个 chunk，写热点
hashed _id 写入均匀，但查"某篇文章的评论"要广播到所有分片
target_id 同一对象的评论集中在一个分片，查询只命中一个分片；但爆款对象可能形成热点、产生超大 chunk
{target_id: 1, _id: 1} 复合片键 查询能定向路由，同一对象数据过多时还能继续拆分 chunk，推荐 
sh.enableSharding("blog")
sh.shardCollection("blog.comments", { target_id: 1, _id: 1 })

原则：片键要满足最常见的查询（定向路由），同时有足够的基数和分布，避免单调递增。

09.其他注意点

  • 敏感词与审核：写入前过敏感词，新评论 status=0，审核通过才展示（或先展示给自己看）；
  • 删除：使用软删除（status=2），保留回复关系，展示为"该评论已删除"；
  • 防刷：同一用户评论频率限流（Redis 计数）；
  • 写关注（write concern）：评论可以用默认的 w: "majority" 保证主从切换不丢数据。

10.面试题速答

  • 评论数据怎么建模？ 独立 comments 集合 + root_id/parent_id 两级结构，冗余用户展示信息，一级评论内嵌少量热门回复。
  • 为什么不全部内嵌？ 16MB 文档上限、写放大、无法独立分页。
  • 分页怎么做？ 游标分页，(created_at, _id) 作为游标，避免深分页 skip。
  • 片键怎么选？ {target_id, _id} 复合片键，兼顾定向查询和数据分布。
  • 点赞防重复？ 明细集合唯一索引 + $inc 原子计数。

小结

  • 评论适合 MongoDB：量大、结构灵活、查询模式简单；
  • 建模用"引用为主，内嵌少量热门回复"，两级扁平结构最实用；
  • 分页用游标，索引遵循 ESR 原则；
  • 计数用 $inc 或 Redis 聚合，点赞用唯一索引防重复；
  • 分片选复合片键，避免单调递增导致写热点。
