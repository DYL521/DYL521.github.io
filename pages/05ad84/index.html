16.排行榜实现

https://www.cnblogs.com/xiaonq/p/14268218.html

  • es / redis

排行榜（积分榜、热度榜、销量榜、游戏战力榜）是面试常问的项目点。数据量不大时可以直接 ORDER BY，但实时性要求高、访问量大的场景，基本都会用 Redis 有序集合（ZSET） 实现。

01.为什么用 ZSET

用 MySQL 实现排行榜的问题：

  • ORDER BY score DESC LIMIT 每次都要排序，数据量大时慢；
  • 查询"我排第几名"需要 COUNT(*) WHERE score > 我的分数，高并发下压力大；
  • 分数频繁变化，频繁更新索引。

ZSET 的特点：

  • 成员（member）唯一，每个成员关联一个 double 类型的分数（score），自动按分数排序；
  • 底层是 跳表（skiplist）+ 哈希表（元素少时用紧凑编码 listpack，旧版本是 ziplist）；
  • 更新分数、查排名、范围查询的时间复杂度都是 O(log N) 级别（范围查询再加上返回元素数 M）。

02.常用命令

# 添加/更新分数
ZADD rank:score 100 user:1 80 user:2 95 user:3

# 分数增加（不存在则从 0 开始）
ZINCRBY rank:score 10 user:2

# 前 10 名（从高到低），带分数
ZREVRANGE rank:score 0 9 WITHSCORES
# Redis 6.2+ 推荐写法
ZRANGE rank:score 0 9 REV WITHSCORES

# 某用户的排名（从 0 开始，高分在前）
ZREVRANK rank:score user:2

# 某用户的分数
ZSCORE rank:score user:2

# 榜单总人数
ZCARD rank:score

# 分数区间内的人数
ZCOUNT rank:score 90 100

# 移除成员
ZREM rank:score user:3

03.Python 实现

import redis

r = redis.Redis(host="127.0.0.1", port=6379, decode_responses=True)
KEY = "rank:score"


def add_score(user_id, delta):
    """用户加分"""
    return r.zincrby(KEY, delta, f"user:{user_id}")


def top_n(n=10):
    """前 n 名"""
    return r.zrevrange(KEY, 0, n - 1, withscores=True)


def my_rank(user_id):
    """我的名次（从 1 开始）和分数，没上榜返回 None"""
    member = f"user:{user_id}"
    pipe = r.pipeline()
    pipe.zrevrank(KEY, member)
    pipe.zscore(KEY, member)
    rank, score = pipe.execute()
    if rank is None:
        return None
    return rank + 1, score


def page(page_no, page_size=20):
    """分页查询，page_no 从 1 开始"""
    start = (page_no - 1) * page_size
    return r.zrevrange(KEY, start, start + page_size - 1, withscores=True)

ZSET 里只存 user_id，昵称、头像等展示信息不要塞进 member，查出 ID 后再批量从缓存（如 Hash 或 MGET）取，这样改昵称不影响排行榜。

04.同分怎么排：按时间先后

ZSET 分数相同时按 member 的字典序排序，这通常不符合业务需求（一般要求"同分时先达到的排前面"）。

常见做法是把时间编码进 score：

score = 业务分数 * 10^10 + (MAX_TS - 达到该分数的时间戳秒)
  • MAX_TS 取一个足够大的未来时间戳（例如 2100 年对应的 4102444800）；
  • 时间越早，MAX_TS - ts 越大，同分时排在前面；
  • 展示时 业务分数 = int(score // 10**10)。
import time

MAX_TS = 4102444800
FACTOR = 10 ** 10


def set_score(user_id, real_score):
    ts = int(time.time())
    r.zadd(KEY, {f"user:{user_id}": real_score * FACTOR + (MAX_TS - ts)})


def real_score(score):
    return int(score // FACTOR)

精度坑：score 是 double，能精确表示的整数上限约为 2^53 ≈ 9×10^15。上面的编码中时间部分占 10 位，业务分数最多只能到约 10^5 量级。分数更大时要缩短时间部分（比如用"相对于活动开始时间的秒数"）或者改用其他方案（例如同分时再查一个存时间的 Hash 做二次排序）。

另外加分时要注意：如果用 ZINCRBY 直接加 delta * FACTOR，时间部分不会刷新为"最新达到时间"，需要用 Lua 脚本读出旧分数、重新计算后 ZADD，保证原子性：

-- KEYS[1]=榜单 key, ARGV[1]=member, ARGV[2]=delta, ARGV[3]=当前时间戳
local old = redis.call('ZSCORE', KEYS[1], ARGV[1])
local real = 0
if old then real = math.floor(tonumber(old) / 1e10) end
real = real + tonumber(ARGV[2])
local score = real * 1e10 + (4102444800 - tonumber(ARGV[3]))
-- 用 %.0f 转成整数字符串，避免 Lua 默认的 %.14g 格式丢失精度
redis.call('ZADD', KEYS[1], string.format('%.0f', score), ARGV[1])
return real

05.日榜、周榜、月榜

按周期拆 key，比如：

rank:day:20210212
rank:week:2021-06
rank:month:202102

方案一：写入时同时更新多个榜（用 pipeline 批量执行）：

def add_score_all(user_id, delta):
    member = f"user:{user_id}"
    day = time.strftime("%Y%m%d")
    pipe = r.pipeline()
    pipe.zincrby(f"rank:day:{day}", delta, member)
    pipe.expire(f"rank:day:{day}", 3 * 86400)   # 日榜保留 3 天
    pipe.zincrby("rank:total", delta, member)
    pipe.execute()

方案二：只写日榜，周榜/月榜用 ZUNIONSTORE 合并：

ZUNIONSTORE rank:week:2021-06 7 rank:day:20210208 rank:day:20210209 rank:day:20210210 \
  rank:day:20210211 rank:day:20210212 rank:day:20210213 rank:day:20210214 AGGREGATE SUM

合并成本是 O(N) 级别，适合定时任务计算（比如每小时刷新一次），不适合每次请求都算。

记得给周期性 key 设置过期时间，否则历史榜单会一直占用内存。

06.分页与"我的排名"

  • 分页直接用 ZREVRANGE start stop，因为跳表支持按排名快速定位，不存在 MySQL 深分页的问题；
  • “我的排名附近的人”：先 ZREVRANK 取到排名 r，再 ZREVRANGE r-5 r+5；
  • 未上榜返回 nil，前端显示"未上榜"；
  • 大榜单通常只展示 Top 100 / Top 1000，超出部分只显示"1000+"。

07.大 key 问题

一个 ZSET 存几百万甚至上千万成员时会成为大 key：

  • DEL 大 key 会阻塞主线程 → 用 UNLINK 异步删除，或开启 lazyfree-lazy-* 相关配置；
  • 一次性 ZRANGE 0 -1 返回全部数据会阻塞 → 只取需要的范围，遍历用 ZSCAN；
  • 迁移、主从全量同步变慢；集群模式下一个 key 只能在一个分片，形成数据和访问热点。

优化思路：

  • 只保留需要展示的部分：例如只关心前 1 万名，定期用 ZREMRANGEBYRANK key 0 -10001 裁剪掉排在 1 万名之后的成员（升序下标，从低分端删除）；
  • 分桶：按分数段或用户 ID 哈希拆成多个 ZSET，查 Top N 时各桶取 Top N 再在应用层归并；
  • 区分"全量排名"和"展示榜"：全量精确排名可以离线算，在线只维护 Top N。

08.持久化与可靠性

  • 排行榜通常以 MySQL 中的明细或总分为准，Redis 是可重建的视图；Redis 数据丢失后可以从数据库重新加载；
  • 开启 AOF（appendfsync everysec）最多丢失约 1 秒的数据，配合 RDB 做备份；
  • 部署主从 + 哨兵或 Cluster 保证高可用；
  • 活动结束后把最终榜单快照写入数据库，作为发奖依据，不要直接依赖 Redis 里的实时数据。

09.为什么提到 ES

原文提到 “es / redis”：

  • Redis ZSET：适合单维度分数、实时更新、实时查排名的场景；
  • Elasticsearch：适合多条件过滤后排序（例如"某城市、某分类下销量排行"），维度组合很多时不可能给每种组合都建一个 ZSET，用 ES 按条件查询再排序更灵活，但实时性和"查我排第几"不如 Redis 直接。

10.面试题速答

  • 排行榜为什么用 ZSET？ 自动排序，更新、查排名、取 Top N 都是对数复杂度。
  • ZSET 底层结构？ 跳表 + 哈希表，元素少时用 listpack（旧版 ziplist）紧凑编码。
  • 同分怎么按时间排？ 把时间戳编码进 score 的低位，注意 double 精度上限。
  • 日榜周榜怎么做？ 按日期拆 key + 过期时间，周榜用 ZUNIONSTORE 定时合并。
  • 榜单太大怎么办？ 只保留 Top N、分桶、UNLINK 删除、避免全量 ZRANGE。
  • Redis 挂了排行榜丢了怎么办？ 数据库是数据源，Redis 可重建；AOF + 主从保证可用性。

小结

  • 实时排行榜首选 Redis ZSET：ZINCRBY 加分、ZREVRANGE 取榜、ZREVRANK 查名次；
  • 同分按时间排需要把时间编码进 score，注意精度；
  • 周期榜单按 key 拆分并设置过期，合并用 ZUNIONSTORE；
  • 关注大 key，只维护需要展示的 Top N；
  • Redis 是可重建的视图，最终数据以数据库为准。
