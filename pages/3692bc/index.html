01.JWT 与单点登录是什么关系

**单点登录（SSO）**解决的是“登录一次，如何访问多个相互信任的应用”；**JWT（JSON Web Token）**是一种自包含的令牌格式。二者不是同一个概念：JWT 可以作为 SSO 中传递身份信息的凭证，但完整的 SSO 还需要统一认证中心、应用间跳转、令牌校验、退出与吊销机制。

与基于 Redis 的服务端 Session 方案相比，资源服务验证 JWT 时通常不必查询中心存储，因此扩展方便、跨服务传递简单；代价是令牌签发后难以立即失效，而且载荷会随请求传输。

02.一次完整的登录与访问流程

下面以“统一认证中心 + 业务应用 + 资源服务”为例。浏览器先通过授权码完成登录，业务后端再取得 JWT；不要把 JWT 直接拼在重定向 URL 中。

sequenceDiagram
    autonumber
    participant U as 浏览器
    participant A as 业务应用
    participant S as 统一认证中心
    participant R as 资源服务

    U->>A: 访问受保护页面
    A->>U: 跳转认证中心，携带 redirect_uri、state
    U->>S: 完成登录与授权
    S->>U: 携带一次性授权码回调应用
    U->>A: 提交授权码与 state
    A->>A: 校验 state
    A->>S: 后端用授权码换取 JWT
    S-->>A: 返回短期访问令牌与刷新令牌
    A-->>U: 建立本站登录会话
    U->>A: 请求受保护 API
    A->>R: Authorization: Bearer 访问令牌
    R->>R: 用可信公钥验签并校验声明
    R-->>A: 返回受保护资源
    A-->>U: 返回处理结果

授权码应只能使用一次并设置很短的有效期。公开客户端（如纯 SPA、移动端）无法安全保存 client_secret，应使用授权码模式加 PKCE；传统服务端应用可以由后端保存密钥并完成换令牌。

03.JWT 的三个部分

JWT 的外观是三段由点分隔的 Base64URL 文本：

base64url(header).base64url(payload).base64url(signature)

{
  "alg": "RS256",
  "typ": "JWT",
  "kid": "sso-key-2026-01"
}

{
  "sub": "user-1001",
  "iss": "https://sso.example.com",
  "aud": "order-api",
  "iat": 1735689600,
  "exp": 1735690500,
  "jti": "a-unique-token-id"
}
  • Header：签名算法、令牌类型和密钥 ID。
  • Payload：用户标识、签发者、受众、签发时间、过期时间等声明。
  • Signature：对前两段编码结果及分隔点进行签名，用于发现篡改和确认签发者。

**Base64URL 只是编码，不是加密。**任何拿到令牌的人都能解码 Header 和 Payload，因此默认不能把密码、身份证号等敏感信息放进去。需要保密内容时，应使用 JWE 或只传不透明引用，而不是误以为普通 JWT 已加密。

04.RSA 在 RS256 中做什么

RS256 使用的是 RSA 数字签名 + SHA-256，不是用 RSA 加密整个 JWT：

  1. 认证中心保管私钥，对令牌的签名输入计算摘要并生成签名。
  2. 业务服务从预先配置的公钥或可信 JWKS 地址取得公钥。
  3. 业务服务用公钥验证签名，从而确认令牌确实由认证中心签发且内容未被修改。

私钥只能存在于认证中心；公钥可以分发，但必须来自可信来源。业务方不能因为“公钥可以公开”就接受令牌自己提供的任意 JWKS 地址。

05.资源服务必须校验什么

只解析 Payload 而不验签等于没有认证。一个完整的校验过程至少包括：

  1. 限定算法：服务端明确只允许 RS256，拒绝 none，不能根据令牌中的 alg 临时切换成不安全的验证逻辑。
  2. 选择密钥：根据 kid 从可信密钥集合中选公钥，并支持旧公钥短期保留、密钥轮换和缓存刷新。
  3. 验证签名：签名不通过直接返回 401。
  4. 校验时间：检查 exp、nbf、iat，只允许很小的时钟偏差；过期令牌不能因为签名正确而继续使用。
  5. 校验签发者和受众：iss 必须是本站信任的认证中心，aud 必须包含当前服务，避免把给其他系统的令牌拿过来用。
  6. 校验业务身份：确认 sub 对应的用户仍被允许访问；涉及 OIDC 登录时还要校验 nonce。
# 伪代码：具体参数名以所用 JWT 库为准
payload = jwt.decode(
    token,
    public_key,
    algorithms=["RS256"],
    issuer="https://sso.example.com",
    audience="order-api",
    options={"require": ["sub", "iss", "aud", "iat", "exp", "jti"]},
)

不要在生产代码里手写 Base64 解码后就直接信任 sub，也不要为了“兼容”关闭签名或过期校验。

06.访问令牌、刷新令牌与退出

常见做法是把两种令牌分开：

类型 有效期 用途 泄露后的影响
Access Token 几分钟到十几分钟 调用资源 API 在过期前可能被直接使用
Refresh Token 数天到数周，支持轮换 到认证中心换新的访问令牌 风险更高，必须严格保存并可吊销

浏览器退出登录时，至少要清除本站会话和本地凭据，并在认证中心吊销刷新令牌。如果要求所有应用立即退出，还要让认证中心结束 SSO 会话，并使各应用删除自己的会话。

“JWT 无状态”只表示资源服务可以不保存访问令牌会话，不代表整个认证系统没有任何状态。用户、授权、刷新令牌通常仍需持久化；如果通过 jti 黑名单立即吊销访问令牌，也就重新引入了状态查询。这是安全与架构成本之间的取舍，不是实现错误。

07.浏览器如何保存凭据

方案 优点 主要风险与适用场景
BFF/后端保存令牌，浏览器只持有 HttpOnly Session Cookie JavaScript 读不到访问令牌，攻击面较小 要防 CSRF；Cookie 设置 Secure、合适的 SameSite 和作用域
SPA 内存保存访问令牌 不持久化到磁盘，刷新页面后重新获取 XSS 仍能读取内存；需要可靠的刷新机制
localStorage 长期保存访问/刷新令牌 实现简单、跨刷新保留 XSS 可直接窃取，不建议用于高安全场景

没有一种存储方式能替代 XSS 防护。输入转义、内容安全策略、依赖治理和减少敏感令牌暴露时间仍然必要。

08.常见问题与面试回答

  • **JWT 能防止篡改吗？**能，前提是正确验签；但它默认不防读取。
  • **JWT 能实现单点登录吗？**它是凭证格式，SSO 还需要认证中心和跨应用登录流程。
  • **JWT 过期了怎么办？**用可吊销、最好带轮换和重用检测的刷新令牌换新的访问令牌，而不是无限延长访问令牌。
  • **用户被禁用后怎么办？**缩短访问令牌有效期，吊销刷新令牌；高安全接口再查询用户状态或令牌版本。
  • **所有请求都查用户状态还能叫无状态吗？**资源服务增加了状态依赖，但往往是为了满足安全要求，应按业务风险选择，而不是追求概念上的“纯无状态”。

生产环境还必须全程使用 HTTPS，精确校验回调地址，保护授权码交换过程，避免在日志中记录完整令牌，并限制令牌权限范围（scope）。
