Django实现读写分离

Python 2021-02-17 · 更新于 2026-11-21 · 6 分钟阅读 · 1674 字

01.为什么要读写分离

大多数 Web 应用都是读多写少。当单台数据库扛不住压力时，常见做法是搭建 MySQL/PostgreSQL 的主从复制：

  • 主库（Primary/Master）：负责所有写操作（INSERT/UPDATE/DELETE），并把变更同步给从库。
  • 从库（Replica/Slave）：只负责读操作，可以有多台，分摊查询压力。

数据库层面的主从复制由 DBA 或云数据库配置完成，应用层要做的就是：写请求发给主库，读请求发给从库。Django 原生支持多数据库，通过 using() 手动指定，或者通过**数据库路由（Database Router）**自动分发。

02.配置多个数据库

# settings.py
DATABASES = {
    "default": {                       # 主库，负责写
        "ENGINE": "django.db.backends.mysql",
        "NAME": "testdb",
        "USER": "django",
        "PASSWORD": "******",
        "HOST": "10.0.0.1",
        "PORT": "3306",
    },
    "replica1": {                      # 从库 1
        "ENGINE": "django.db.backends.mysql",
        "NAME": "testdb",
        "USER": "django_ro",
        "PASSWORD": "******",
        "HOST": "10.0.0.2",
        "PORT": "3306",
        "TEST": {"MIRROR": "default"},  # 跑测试时把它当作 default 的镜像
    },
    "replica2": {                      # 从库 2
        "ENGINE": "django.db.backends.mysql",
        "NAME": "testdb",
        "USER": "django_ro",
        "PASSWORD": "******",
        "HOST": "10.0.0.3",
        "PORT": "3306",
        "TEST": {"MIRROR": "default"},
    },
}

说明：

  • 必须有一个名为 default 的库（可以为空字典，但一般就用它做主库）。
  • 从库建议使用只读账号，即使代码写错也不会误写从库。
  • TEST.MIRROR 让测试时从库指向测试主库，否则测试中写入主库的数据在“从库”上读不到。

03.方式一：手动指定 using()

from app01.models import Book

# 读：从从库读取
books = Book.objects.using("replica1").filter(price__gt=50)

# 写：写入主库
Book.objects.using("default").create(title="Django", price=88)

book = Book(title="Flask", price=66)
book.save(using="default")
book.delete(using="default")

手动指定最直观，但每个查询都要写，容易遗漏，只适合少量特殊场景（比如某个报表接口强制走从库）。

04.方式二：数据库路由（推荐）

路由器是一个普通的类，可以实现以下四个方法（都是可选的，返回 None 表示“我不管，交给下一个路由器”）：

方法 作用
db_for_read(model, **hints) 读操作使用哪个库
db_for_write(model, **hints) 写操作使用哪个库
allow_relation(obj1, obj2, **hints) 两个对象之间是否允许建立关联（外键、多对多）
allow_migrate(db, app_label, model_name=None, **hints) 某个 app/模型是否允许在 db 上执行迁移

4.1 编写路由器

# utils/db_router.py
import random


class PrimaryReplicaRouter:
    replicas = ["replica1", "replica2"]

    def db_for_read(self, model, **hints):
        # 随机选一个从库，实现简单的负载均衡
        return random.choice(self.replicas)

    def db_for_write(self, model, **hints):
        return "default"

    def allow_relation(self, obj1, obj2, **hints):
        # 主从是同一份数据，允许不同库读出的对象之间建立关联
        db_set = {"default", *self.replicas}
        if obj1._state.db in db_set and obj2._state.db in db_set:
            return True
        return None

    def allow_migrate(self, db, app_label, model_name=None, **hints):
        # 只在主库执行迁移，从库的表结构通过主从复制同步
        return db == "default"

4.2 注册路由器

# settings.py
DATABASE_ROUTERS = ["utils.db_router.PrimaryReplicaRouter"]

DATABASE_ROUTERS 是一个列表，Django 会按顺序询问每个路由器，第一个返回非 None 的结果生效；都返回 None 时使用 default。

配置之后业务代码不需要任何改动：

Book.objects.filter(price__gt=50)      # 自动走 replica1 / replica2
Book.objects.create(title="Django")    # 自动走 default

显式调用 using() 的优先级高于路由器。

4.3 迁移

python manage.py migrate                    # 默认对 default 执行
python manage.py migrate --database=replica1  # 对从库执行时，allow_migrate 返回 False 的模型会被跳过

05.按 app 分库

路由器不仅能做读写分离，还能实现垂直分库，比如把日志类 app 放到单独的库：

class LogRouter:
    route_app_labels = {"logs"}

    def db_for_read(self, model, **hints):
        if model._meta.app_label in self.route_app_labels:
            return "log_db"
        return None

    def db_for_write(self, model, **hints):
        if model._meta.app_label in self.route_app_labels:
            return "log_db"
        return None

    def allow_migrate(self, db, app_label, model_name=None, **hints):
        if app_label in self.route_app_labels:
            return db == "log_db"
        return None

多个路由器组合时，把更具体的放前面：DATABASE_ROUTERS = ["utils.db_router.LogRouter", "utils.db_router.PrimaryReplicaRouter"]。

06.主从延迟问题（重点）

主从复制通常是异步的，从库的数据会比主库晚一点（毫秒到秒级，压力大时更久）。典型问题：用户刚提交了修改，立刻跳转到详情页，从从库读出来的还是旧数据。

常见解决思路：

  1. 写后读主：对“刚写完马上要读”的场景，手动 using("default")。
  2. 请求级粘滞：一个请求里只要发生过写操作，之后的读都走主库。可以用 contextvars 记录标记，在中间件中初始化：
# utils/db_router.py
import contextvars
import random

_use_primary = contextvars.ContextVar("use_primary", default=False)


class StickyPrimaryReplicaRouter:
    replicas = ["replica1", "replica2"]

    def db_for_read(self, model, **hints):
        if _use_primary.get():
            return "default"
        return random.choice(self.replicas)

    def db_for_write(self, model, **hints):
        _use_primary.set(True)        # 发生过写，后续读走主库
        return "default"

    def allow_relation(self, obj1, obj2, **hints):
        return True

    def allow_migrate(self, db, app_label, model_name=None, **hints):
        return db == "default"


# utils/middleware.py
class ResetPrimaryFlagMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        token = _use_primary.set(request.method not in ("GET", "HEAD", "OPTIONS"))
        try:
            return self.get_response(request)
        finally:
            _use_primary.reset(token)

（中间件中需要 from utils.db_router import _use_primary。）这里非安全方法（POST/PUT/DELETE 等）的请求直接全程走主库，简单可靠。

  1. 跨请求粘滞：写操作后在 Cookie 或缓存里记一个短时间标记（例如几秒），期间该用户的读请求都走主库。
  2. 业务上容忍：对一致性要求不高的列表、统计页，直接接受短暂延迟。

07.常见坑

  1. 事务里的读也会被路由到从库：transaction.atomic() 默认只作用于 default 连接，事务内的 Model.objects.get() 仍然会经过 db_for_read 走从库，读不到事务中尚未提交的数据。需要在事务里读时，显式 using("default") 或使用上面的“写后读主”策略。
  2. select_for_update() 必须在主库：它要加行锁，应配合 using("default") 并放在事务中使用。
  3. 跨库关联：Django 不支持跨数据库的外键和 JOIN。读写分离中主从是同一份数据，所以在 allow_relation 里放行即可；但真正的分库（不同数据）之间不能建立关联。
  4. 迁移只跑主库：从库的表结构依赖复制同步，不要在从库上直接执行迁移。
  5. 路由器拿到的是模型类：db_for_read 里能用到的主要是 model._meta.app_label、model._meta.model_name 和 hints（如 hints["instance"]），无法直接拿到 request，需要请求信息时借助 contextvars 等手段。

08.小结

  • Django 通过 DATABASES 配置多个库，通过 using() 或 DATABASE_ROUTERS 决定每个查询用哪个库。
  • 路由器四个方法：db_for_read、db_for_write、allow_relation、allow_migrate，返回 None 表示交给下一个路由器。
  • 读写分离最大的问题是主从延迟，常用“写后读主 / 请求内粘滞主库”解决。
  • 事务、select_for_update 等需要强一致的场景要显式走主库。
