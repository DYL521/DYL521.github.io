《Git》学习笔记

代码管理 2020-11-18 · 更新于 2026-11-21 · 9 分钟阅读 · 2482 字

01.Git 是什么

Git 是一个分布式版本控制系统。与 SVN 这类集中式系统不同，每个开发者克隆下来的都是完整仓库（包含全部历史），提交、查看历史、创建分支都在本地完成，速度快且不依赖网络，远程仓库只是用来交换数据的"另一个副本"。

Git 的几个设计特点：

  • 直接记录快照，而不是差异：每次提交保存的是整个项目在那一刻的快照（未修改的文件只存一个指向旧对象的引用）。
  • 几乎所有操作都在本地执行。
  • 完整性校验：所有对象都以内容的哈希值（默认 SHA-1，新版本也支持 SHA-256 仓库）作为名字，内容被篡改会被立刻发现。
  • 一般只添加数据：提交过的内容很难真正丢失，这也是各种"后悔药"能生效的基础。

本目录下的笔记以 Git 官方中文文档（Pro Git） 为准，本文作为总览，梳理最核心的概念；具体命令见"手册"和"文档笔记"中的各篇。

02.三个区域与文件状态

flowchart LR
    W[工作区
Working Directory] -- git add --> S[暂存区
Index / Stage]
    S -- git commit --> R[本地仓库
.git 目录]
    R -- git push --> RR[远程仓库]
    RR -- git fetch / pull --> R
    R -- git switch / restore --> W
区域 说明
工作区 实际看到和编辑的文件
暂存区（Index） .git/index 文件，记录"下一次提交将包含什么"
本地仓库 .git 目录，保存所有对象和引用

文件状态：未跟踪（untracked）→ 已暂存（staged）→ 已提交（committed）→ 已修改（modified）。git status 查看状态，git diff 看工作区与暂存区的差异，git diff --staged 看暂存区与最新提交的差异。

暂存区的意义在于：可以把一次修改拆成多个有意义的提交（配合 git add -p 按块暂存）。

03.对象模型：Git 如何存储数据

.git/objects 中存放四种对象：

对象 内容
blob 文件内容（不含文件名）
tree 目录结构：文件名、权限、指向 blob 或子 tree 的哈希
commit 指向一个顶层 tree，以及父提交、作者、提交者、提交信息
tag 附注标签对象，指向某个提交并带有标签信息 
flowchart TD
    C2[commit 2] -->|parent| C1[commit 1]
    C2 --> T2[tree /]
    T2 --> B1[blob README]
    T2 --> T3[tree src/]
    T3 --> B2[blob main.java]
    C1 --> T1[tree /]
    T1 --> B1

可以用底层命令亲自观察：

git cat-file -t HEAD            # 查看对象类型：commit
git cat-file -p HEAD            # 查看 commit 内容：tree、parent、author
git cat-file -p HEAD^{tree}     # 查看顶层 tree
git rev-parse HEAD              # 查看当前提交的完整哈希

引用（ref） 是指向提交的"指针"，本质是存放哈希值的文件：

  • 分支：.git/refs/heads/main
  • 远程跟踪分支：.git/refs/remotes/origin/main
  • 标签：.git/refs/tags/v1.0
  • HEAD：.git/HEAD，通常是对当前分支的符号引用（ref: refs/heads/main）。HEAD 直接指向某个提交而不是分支时，称为"分离头指针（detached HEAD）"。

理解这一点后，很多命令就很好解释了：分支只是一个指向提交的可移动指针，所以创建分支只是写一个 41 字节的文件，几乎是瞬间完成的。

04.分支

git branch                      # 查看本地分支
git branch -vv                  # 查看分支与上游的跟踪关系
git switch -c feature/login     # 创建并切换（Git 2.23+，替代 git checkout -b）
git switch main                 # 切换分支
git branch -d feature/login     # 删除已合并的分支（-D 强制删除）
git push -u origin feature/login   # 推送并建立跟踪关系

Git 2.23 引入了 git switch（切换分支）和 git restore（恢复文件），把过去职责过多的 git checkout 拆分开，更不容易误操作。

4.1 远程分支

  • origin/main 是远程跟踪分支，是上一次与远程通信时远程 main 的位置，只能通过 fetch 更新，不能直接在上面提交。
  • git fetch 只下载数据、更新远程跟踪分支，不改动工作区；git pull = git fetch + git merge（或配置为 rebase）。

05.合并：merge 与 rebase

两者都用于把一个分支的修改整合到另一个分支。

5.1 merge

git switch main
git merge feature/login
  • 快进合并（fast-forward）：main 没有新提交时，直接把 main 指针移动到 feature 的最新提交，不产生新提交。
  • 三方合并：两条分支都有新提交时，以共同祖先为基础做三方合并，生成一个有两个父提交的合并提交。
  • git merge --no-ff 强制生成合并提交，保留"这里合并过一个功能分支"的痕迹。

5.2 rebase

git switch feature/login
git rebase main                 # 把 feature 上的提交"搬"到 main 最新提交之后
git switch main
git merge feature/login         # 此时可以快进合并

gitGraph
    commit id: "A"
    commit id: "B"
    branch feature
    commit id: "C"
    commit id: "D"
    checkout main
    commit id: "E"

上图中，merge 会生成合并提交 M（父提交为 E 和 D）；rebase 则会把 C、D 重新应用到 E 之后，生成新的 C’、D’（哈希改变），历史变成一条直线 A-B-E-C’-D’。

对比 merge rebase
历史 保留真实的分叉与合并 线性、整洁
是否改写提交 否 是，生成新提交
冲突处理 一次性解决 每个提交可能都要解决一次
适用 合并公共分支、功能分支合入主干 整理本地尚未推送的提交、同步主干最新代码

变基的黄金法则：不要对已经推送并被他人使用的提交执行变基。 否则别人基于旧提交的工作会与新提交冲突，历史会变得混乱。

交互式变基 git rebase -i HEAD~3 可以对最近的提交进行合并（squash/fixup）、改提交信息（reword）、调整顺序、删除。

5.3 解决冲突

git status                      # 查看冲突文件
# 编辑文件，处理 <<<<<<< ======= >>>>>>> 标记
git add <file>
git merge --continue            # 或 git rebase --continue
git merge --abort               # 放弃本次合并，回到合并前

06.撤销操作（后悔药）

场景 命令
丢弃工作区修改 git restore <file>
取消暂存（保留修改） git restore --staged <file>
修改最后一次提交（信息或补漏文件） git commit --amend
撤销提交，修改回到暂存区 git reset --soft HEAD~1
撤销提交，修改回到工作区（默认） git reset --mixed HEAD~1
撤销提交并丢弃修改（危险） git reset --hard HEAD~1
撤销已推送的提交 git revert <commit>
临时保存修改 git stash / git stash pop
找回"丢失"的提交 git reflog + git reset --hard <hash> 或 git branch <name> <hash>

6.1 reset 三种模式

git reset <commit> 都会把当前分支指针移动到目标提交，区别在于是否同时更新暂存区和工作区：

模式 移动分支指针 重置暂存区 重置工作区
--soft ✓
--mixed（默认） ✓ ✓
--hard ✓ ✓ ✓

6.2 reset 与 revert

  • reset 移动指针、改写历史，适合本地还没推送的提交。
  • revert 新建一个"反向提交"抵消指定提交的修改，不改写历史，适合已推送到公共分支的提交。

6.3 reflog

git reflog 记录了 HEAD 和分支指针的每一次移动（默认保留约 90 天）。即使执行了 reset --hard 或误删了分支，只要提交曾经存在过，几乎都能通过 reflog 找回。唯一真正找不回的是从未提交、也从未 add 过的工作区修改。

07.协作工作流

7.1 常见分支模型

  • Git Flow：main（发布）、develop（开发）、feature/*、release/*、hotfix/*。流程完整，适合有固定发布周期的项目，但分支较多。
  • GitHub Flow：只有 main 和功能分支，功能分支通过 Pull Request 评审后合并到 main 并部署。简单，适合持续部署。
  • 主干开发（Trunk-Based）：所有人频繁向主干提交小改动，配合功能开关和完善的 CI。

7.2 一次典型的功能开发

git switch main && git pull                 # 同步最新主干
git switch -c feature/order-export          # 新建功能分支
# ... 编码 ...
git add -p                                  # 按块挑选要提交的修改
git commit -m "feat: 订单导出支持 Excel"
git fetch origin && git rebase origin/main  # 同步主干（仅限自己的分支）
git push -u origin feature/order-export     # 推送并发起 PR/MR

推送被拒（远程有新提交）时，先 git pull --rebase 再推送；对自己的功能分支执行变基后需要强推时，使用更安全的 git push --force-with-lease，它会在远程分支被他人更新过时拒绝覆盖。

08.常见问题

  1. 提交了不该提交的文件：已被跟踪的文件加入 .gitignore 不会生效，需要先 git rm --cached <file> 取消跟踪。
  2. 在 detached HEAD 上提交：切走后提交没有分支引用，及时 git switch -c <新分支> 保存。
  3. 换行符问题：Windows 与 Linux 混合开发时配置 core.autocrlf，或在仓库中用 .gitattributes 统一规范。
  4. 误把密钥推送到远程：仅删除文件再提交并不够，历史中仍然存在，应立即作废密钥，再用 git filter-repo 等工具清理历史。
  5. git pull 产生大量无意义的合并提交：配置 git config --global pull.rebase true，或使用 git pull --rebase。

小结

  • Git 是分布式的，本地仓库保存完整历史，数据以 blob / tree / commit / tag 对象存储，用哈希寻址。
  • 三个区域：工作区 → 暂存区 → 本地仓库，再与远程仓库同步。
  • 分支只是指向提交的指针，HEAD 指向当前分支，因此分支创建和切换都非常轻量。
  • merge 保留真实历史，rebase 让历史线性；不要变基已推送的公共提交。
  • 撤销操作：本地未推送用 reset / --amend，已推送用 revert，找回丢失的提交靠 reflog。
